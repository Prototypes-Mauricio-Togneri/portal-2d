# Stage 02 — The solver: a game that understands itself

Status: Draft
Last revised: 2026-11-07

## Goal

A program that searches every reachable state of a chamber and answers questions about it. For the author: every chamber is proven solvable on every check, par (fewest moves, fewest portals) is known and stored, and a report shows unintended shortcuts and elements that aren't needed. For the player, if the solver is fast enough in the browser: an optional "you can't finish from here" warning and hints worked out from where they are now. If the solver passes a second test, it also judges generated chambers (daily, endless). The first phase is a timed prototype, and its result decides how much of the rest happens.

## Depends on

**Stage 00**

- Records keyed by permanent chamber id, so par and solver results can be stored by id too.
- The first local check command, which this stage extends.

**Stage 01** — done (2026-11-07). It delivered:

- A **pure step** on the v2 rules: `step(chamber, state, action)` (`src/game/rules/step.ts`) returns the next state (the same object when nothing changed, though it can still report events, such as a refused shot) and its events, and `startChamber(chamber)` gives a chamber's settled start. Every effect lands inside the step, so the original rules' one-frame-late effects are gone, and once the chamber is completed a step changes nothing.
- A **compact, immutable state** (`RulesState`): 24–26 16-bit values in the current chambers, with a `key` for maps (one character per value) and a hash. A step never changes the state it is given.
- **No sounds or browser APIs in the rules** (they report events instead; lint and the scripts' TypeScript project enforce it), so the engine loads under Node. A Web Worker should work the same way but hasn't been tried.
- **tsx** runs the engine scripts under Node (`scripts/`, type-checked by `tsconfig.scripts.json`).
- **Recorded solutions** for every chamber (`ReplayData` format 2: actions plus undo and redo), the replay check (`npm run replay:check`) and behaviour fixtures.
- **Chamber format 2** with a version number and an upgrader, and elements described by data: each definition in `src/game/rules/elements/` declares when it blocks walking and shots, whether it takes portals, whether links reach it, and whether entering or leaving its tile can change the state (`reactsToSubject`, the tiles a walking shortcut must stop on).
- The four inherited bugs README lists are fixed, including the box-button crash (releasing a button linked to a box now does nothing), so the solver never has to model a crash.
- An optional `par` block in format 2 (optional `moves` and `portals`, each a whole number 0 or more), left out of every chamber file, so this stage fills it without a format version bump. The parser reads it; the layout validator ignores it. The chamber hash that recorded solutions pin covers the whole chamber, par included (see B1).
- A fixed **action set** of 11 (`src/game/rules/action.ts`): the four moves, four turns in place, blue, orange and interact. Undo and redo aren't actions; the level handles them.
- **"Moves"**: each step that puts the subject on another tile, a portal crossing included; turning in place counts none, so turns cost no moves. `level.ts` and the replay runner count them by comparing the subject's tile before and after a step; neither a step's result nor its events carry it, so the solver counts the same way. A crossing between two portals that face the same tile counts none. Undone steps keep counting and redo counts nothing (README decision 8). Par uses the same definition.

**Stage 01 as built, 2026-11-07** (kept from its notes when its file was removed):

- The recorded solutions take chamber 1 in 163 moves and 22 portals, chamber 2 in 97 and 16, chamber 3 in 121 and 28: routes that work, not optimal, so not par.
- Two throwaway searches (on the old rules, since deleted, so they can't be re-run) failed. A plain breadth-first search over single presses found nothing in chamber 2 after 2.75 million states (49 presses deep). Treating walking as free and searching over world-changing actions (shots, pick-ups, switches, buttons) reached 13 actions deep before portal pairs times box positions blew up; each chamber needs 20–40 such actions. The solver needs stronger pruning than either.
- Speed budget (`npm run random:walk`, Node 24, the author's machine): about 785,000–1,200,000 steps per second (re-measured 2026-11-07: 789,000–1,200,000). A state is 48–52 bytes of values, about 330 bytes on the heap, its key not included.
- Boxes aren't interchangeable: a box link sends each one back to its own start, and so does a fizzler destroying a carried box. Symmetry reduction must keep box identity unless a chamber has neither box links nor fizzlers (today only chamber 2).

## Steps

Each step: what changes, where, and how it is verified. UI steps must use the `frontend-design` skill.

### Phase A — Prototype (go/no-go)

Rough size of the problem, recounted with the v2 rules' own loader and compiled chamber on 2026-11-07 (the counts match the 2026-11-06 ones; only the bounds changed). "Open tiles" are the non-wall tiles reachable from the start, ignoring blockers; in every current chamber that is every non-wall tile. "Wall sides" are the sides, facing one of those tiles, of walls that take portals (7, 5 and 8 more face walls that refuse portals). "Flags" are the blocked flags the state holds, one per element a link reaches (boxes linked to a switch reset instead of holding a flag). "Buttons" are stored in the state as pressed flags, but left out of the bounds and key below (A3).

| #   | Chamber | Size  | Open tiles | Wall sides | Flags | Boxes | Buttons | State values | Upper bound | With position and facing folded into the region | Key bits (buttons left out) |
| --- | ------- | ----- | ---------- | ---------- | ----- | ----- | ------- | ------------ | ----------- | ----------------------------------------------- | --------------------------- |
| 1   | 1       | 20×20 | 262        | 225        | 6     | 2     | 5       | 26           | ~10^14.4    | ~10^11.4                                        | 53                          |
| 2   | 2       | 23×13 | 189        | 169        | 9     | 2     | 2       | 26           | ~10^14.6    | ~10^11.7                                        | 53                          |
| 3   | 3       | 23×17 | 268        | 212        | 5     | 2     | 4       | 24           | ~10^14.1    | ~10^11.0                                        | 52                          |

The upper bound is tiles × 4 facings × (wall sides + 1)² for the two portals × (tiles + 1)² for the two boxes × 2^flags. Stage 01 dropped the "inside a fizzler" flag, which halved the earlier bounds. Portal pairs (~3–5×10^4) and box placements (~4–7×10^4) dominate. Boxes block neither the subject nor shots (the box definition sets `blocksWalking` and `blocksShots` to `'never'`), so most box placements are equivalent. After the pruning below, the reachable count is a **guess of 10^6–10^8** per chamber. That guess is what this phase measures.

- [x] **A3. State key.** Encode a settled state into a fixed-size key whose bit widths come from each chamber's own counts: subject tile and facing; carried box (none or which one); each portal (closed, or the index of a wall side; the state stores a portal as its wall's column, row and side, so the key maps between the two); each box's tile, except a carried box's, which repeats the subject's; one bit per flag. The completed flag is left out too: a settled state is completed exactly when the subject is on the exit. Stage 01 dropped the "inside a fizzler" flag. Button states are not in the key: the state stores each button's pressed flag, but a step settles only once a pass of the button rule changes nothing, so after settling each equals "a box or the subject is on it" (assert this); decoding recomputes them. The current chambers need 52–53 bits (the table), so one 64-bit key (two 32-bit words) fits. Verified by: decoding a key gives back exactly the state encoded, every value included (encode → decode → encode alone would miss a wrong button, completion or carried box tile, which the key leaves out), on every state along the recorded solutions and 100,000 seeded random steps per chamber (`npm run solver:check`); key width printed per chamber (`npm run solve`). Done 2026-11-07: about 300,000 states survive the key, 52–53 bits.
- [x] **A4. Visited set.** An open-addressing hash set over a `Uint32Array` (two words per key) with a parent link for rebuilding the path; no JavaScript objects per state. Entries are numbered in the order added and the capacity is fixed when the set is made, so a parent link (an entry number) never moves, as it would if it pointed at a table slot and the table grew. Verified by: inserting and finding 10^7 random keys in Node, memory under ~250 MB (`npm run state-set:bench`). Done 2026-11-07: 10^7 keys added in 1.7 s and found in 2.1 s; the set's arrays take 188 MiB, the whole Node process 269 MiB.
- [x] **A5. Tiny test chambers.** Write 4–6 hand-made chambers of about 6×6 in `scripts/solver_fixtures/` (not in the catalogue), each with hand-counted fewest moves and fewest portals. Cover: walking through a portal, carrying a box through a portal, a button held by a box, a switch, a fizzler destroying a carried box, a one-way arrow trap (a dead end). They must pass the layout checks (every edge tile a wall, barrier, door or the exit; the subject and boxes starting on plain floor or a button; at most one box per tile), and `tsconfig.scripts.json` must include `scripts/solver_fixtures/*.json`. Verified by: each file loads through the chamber type without a cast.
- [x] **A6. Baseline search.** A cheapest-first search (Dijkstra) over single actions using stage 01's step, stopping when a completed state is taken off the queue. Breadth-first search over presses would find the fewest presses, not the fewest moves or portals, since turns cost no moves. This is slow, but it is the reference answer. Verified by: it matches the hand counts on every tiny chamber, and the solutions it finds pass the replay check. The replay check runs the tiny chambers' hand-written routes; the solver check replays the routes the search finds. Done 2026-11-07: six tiny chambers, 45–3,328 states each; the search matches all twelve hand counts. On a full chamber it explores about 35,000 states a second.
- [ ] **A7. Macro search.** From a state, flood-fill the subject's walkable tiles with distances under the current flags, respecting one-way arrows. Stop at **event tiles**: tiles whose entry or exit changes state (buttons, fizzlers, the exit: the elements whose definition sets `reactsToSubject`; that marks every fizzler, on or off, which is safe but stops some walks early). Walking between other tiles changes only position, facing and a carried box's tile (lasers, ditches, doors, barriers and arrows only block). Only the target tile is checked, so the subject can always walk off a tile that became blocked under it. A portal crossing is a move into a wall holding a portal on the side facing the subject, both portals open; it is refused when the tile in front of the other portal can't be entered, and leaves the subject facing out of it. Macro actions: walk to tile _t_, then turn and shoot A or D; pick up or drop a box; use a switch; step onto or off an event tile; walk through a portal. The edge cost is steps walked (for fewest moves) or portals placed (for fewest portals). A macro action costs a whole walk, not 0 or 1, so both pars use Dijkstra on the combined cost (moves first and portals to break ties, or the reverse); solvability is breadth-first. Walking uses the rules' own `allowsWay` and `canEnter`, exported from the step, so no walking rule is copied. Turning in place costs no moves, so facing only matters just before a shot (interact works on the subject's own tile, not the one it faces). A turn toward the way the subject already faces moves it. On an arrow the other three directions do nothing, not even turn, and an arrow is only entered along its way, so there the subject always faces the arrow's way. So a state is stored with the subject facing its tile's canonical way (the first way it may move there), which is exact for par too, and cuts states by up to 4×. Every macro edge is expanded into keypresses and replayed through the real step on the tiny chambers. Verified by: same optimums as A6 on every tiny chamber; fewer states (each expansion tries many more actions, so compare the rules' steps too); from every state along the recorded solutions and every state A6 finds on the tiny chambers, each walk and turn the solver builds equals the real step's (`npm run solver:check`).
- [ ] **A8. Region folding (solvability only).** For "is it solvable?", replace the subject's tile by its region's smallest tile index (as Sokoban solvers do). Facing is already dropped in A7. Par search keeps exact tiles at decision points. Verified by: same yes/no as A7 on the tiny chambers and the three real ones.
- [ ] **A9. Box drop pruning.** A box is always dropped on the subject's own tile, never on a switch (interact goes to the switch) or the exit (standing there completes the chamber). Only allow drops on buttons, at the box's start, and where the subject must have free hands next: before a switch (a switch refuses while carrying), before picking up the other box, before entering an active fizzler (which destroys a carried box, as does picking one up inside an active field, and returns it to its start). Pruning could miss an optimum, so compare it with unpruned A7 on the tiny chambers. If par changes anywhere, use pruning for solvability only. Verified by: the comparison table in this file.
- [ ] **A10. Dead states.** After a full search, mark states from which the win can't be reached (reachability backwards over the explored graph). Today switches only ever open things (a use also sends the boxes they link back to their start) and destroyed boxes return to their start, so dead ends come mainly from one-way arrows; this step measures how many there really are. Other dead ends are possible in principle: a box left on a tile that a button release then closes, with nothing to reopen it; an area entered by portal with no wall there that takes portals; a box left beyond a one-way route. Leaving the grid is impossible: outside the edge is wall that takes no portals, and the validator requires an enclosed edge. Verified by: the arrow-trap tiny chamber reports its dead states, and no state along a recorded solution is marked dead.
- [ ] **A11. Measure in Node.** Run solvability and both pars on the three chambers. Record explored states, time and peak memory (`process.memoryUsage`) in a table added to this file. Verified by: the table is filled in.
- [ ] **A12. Measure in a worker.** Run the macro search in a module Web Worker in the dev build (`new Worker(new URL(…, import.meta.url), {type: 'module'})`) on the slowest chamber, from the start and from 10 states taken along its recorded solution, searching both to the win and to the next milestone (D1). ## Local checks added

- `npm run solve`: solves every catalogue chamber; fails when one is unsolvable, when stored par differs from computed par, or when a recorded solution beats par. Results are cached by chamber content and solver/rules version. Joins the check command.
- `npm run solver:check` (in `npm run verify` since A6): the state key survives every state along the recorded solutions and a random walk, and on the tiny test chambers in `scripts/solver_fixtures/` the reference search matches their hand-counted answers.

## Go/no-go points

1. **Solvability too slow (test 1 fails).** Stop after phase A. No solver checks, hints, dead-end warning or generated chambers. Stage 03 keeps new mechanics small and relies on recorded solutions. Stage 05's "publish only what you solved" relies on the creator's replay alone: no par, no shortcut report.
2. **Par too slow (test 2 fails).** Keep the solvability check and the report without par. Stage 04 drops moves and portals medals, or uses par set by the author.
3. **Worker too slow (test 3 fails).** Drop next-move hints and the dead-end warning; keep nudge and highlight hints from precomputed milestones. Stage 05's publish check replays the creator's solution; par is shown only once the author's machine has solved the chamber, or the editor limits chamber size to what the browser can solve.
4. **Generator gate (test 4 fails, or F0 fails).** No daily or endless chambers. Stage 05 can offer featured community chambers instead.
5. **Growth.** If a chamber added in stage 03 or 04 pushes solving over budget, simplify that chamber. No chamber in the campaign is exempt from the solver check.

## Risks

- **The state space grows with boxes and size.** Two boxes give ~4–7×10^4 placements; a third multiplies that by ~250. Notice early: the check prints explored states per chamber; watch the trend as chambers are added.
- **Wrong par from a macro-search bug.** Cross-check with the baseline on tiny chambers. A recorded solution beating par is a hard failure. Each final solution is replayed through the real step.
- **The solver and the game disagree on rules.** Rule effects always come from stage 01's step; only the flood fill is solver code, and its edges are replayed (A7).
- **Browser memory.** A visited set of 10^7 keys needs ~160–250 MB; 10^8 doesn't fit a worker. Hints use a bounded search to the next milestone, never a full solve from the start.
- **Stale par after rule changes.** Stage 03 changes rules; the cache key includes the rules version and the check recomputes par.
- **Hints flatten the challenge.** Tiered hints, an explicit key, and hint use shown on the result (open decision 5).
- **Generated chambers are solvable but dull.** Timebox, quality filters calibrated on hand-made chambers, author review.

## Notes for later stages

- **03 Mechanics.** Every new mechanic must be discrete with a small, finite state that fits the key (a timed button adds a counter per button; a slide floor adds nothing; a beam through portals is recomputed from the state, so it adds nothing if never stored). It must also declare its event tiles, and ship a tiny test chamber with hand-counted answers. Echo adds the whole previous attempt to the state, which likely breaks the solver (README open decision 3).
- **04 Campaign.** Medals use the par stored here. Difficulty shown to players comes from clear rates (if open decision 1 is (c)). Hint use is on the result. The menu entry for daily and endless chambers, if phase F passes. A colour for the hint highlight that respects the colour meanings in AGENTS.md.
- **05 Creator platform.** "Publish only what you solved" needs the solver in a browser worker within budget, or the creator's replay with par marked unknown (go/no-go 3). The editor's size limits come from the phase A measurements. The shortcut report's JSON form is shown to creators. Par travels inside the chamber file, so shared links carry it.
