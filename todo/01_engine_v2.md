# Stage 01 — Engine v2

Status: In progress
Last revised: 2026-11-07

## Goal

The rules become a pure, savable step: _state + one action → next state + events_. Players get unlimited undo and redo, keys they can remap, gamepad support, and rules without the inherited bugs. The author gets recorded solutions that are replayed by a local command on every change, element types described by data (a new mechanic is mostly one file), and a chamber format with a version number. Today's engine is kept only as a reference to prove v2 behaves the same, then deleted.

The stage ships in slices that are each useful on their own: A and B (no player change, replays exist), C (undo), D (input), then E to G (v2 replaces the old rules).

## Depends on

- **Stage 00**
  - Records keyed by permanent chamber id. Replays name chambers by permanent id.
  - The local check command. This stage adds the replay check to it.
  - The analytics events. Phase C adds an undo count next to them.
  - The high-DPI canvas fix. It changes the renderer, so it must land before the renderer is ported in E9, and the pixel comparison in E9 must run at a fixed pixel ratio.

## Decisions made

- 2026-11-06 — Remappable keys and gamepad belong here, in the input rewrite (README decision 2).
- 2026-11-06 — Today's rules are a **reference only**. Every recorded solution runs through both engines, and the differences must match the written list of intended changes. Then the old engine is deleted and all chambers run on v2 with the fixes (README decision 3).
- 2026-11-06 — All checks are local commands run on demand. No cloud CI (README decision 6).
- 2026-11-06 — The inherited rule bugs are fixed here, not in stage 00, because rules stay frozen until v2 (README decision 1).
- 2026-11-06 — Engine scripts run under Node with **tsx**, type-checked by their own `tsconfig.scripts.json` (was open decision 1; built in A6).
- 2026-11-06 — Today's rules moved early to `src/game/classic/`, and v2 will be built in `src/game/rules/` (was open decision 10; done in A1).
- 2026-11-06 — Undo lands on **today's engine**, by restoring snapshots; the restore code is deleted with the old engine (was open decision 2; built in phase C).
- 2026-11-06 — `moves` and `portals` keep counting every step, undone ones included; redo counts nothing; an `undos` count is sent with `chamber_restart`, `chamber_quit`, `chamber_abandon` and `chamber_complete`. Stage 04 picks the medal basis (was open decision 3; built in C4).
- 2026-11-06 — Reset chamber stays a full restart and clears undo and redo; undoing all the way back is the rewind, and the clock keeps running (was open decision 4; built in C6).
- 2026-11-06 — Z undoes and X redoes; remappable after phase D (was open decision 5; built in C3).
- 2026-11-06 — Solutions are saved in development with a dev-only "Download solution" button in the completion dialog, the file named after the chamber (was open decision 9; built in B6).
- 2026-11-07 — Keys are bound by physical position (`KeyboardEvent.code`), with the player's layout labels shown wherever keys appear; AZERTY players' default portal key moves to the key labelled Q (was open decision 6; built in D1 and D4).
- 2026-11-07 — Live play applies the next queued press only once the state has settled, so live play matches the step function (was open decision 7; built in D2).
- 2026-11-07 — The gamepad reaches the game through an app-wide bridge in `src/services/`, so chambers, menus and dialogs all work with a pad (was open decision 8; built in D8).
- 2026-11-07 — One key per action. A left/right modifier pair counts as one key, so the default turn key is either Ctrl (D1, D6).
- 2026-11-07 — Escape, Tab, Alt, Meta and the F-keys can't be bound: Escape and Tab belong to the screens, Alt and Meta combinations and the F-keys to the browser (bound to turn, Alt+Left would go Back mid-chamber) (D6).
- 2026-11-07 — D1 to D7 ship as one release, so binding by position never ships while the legend still shows fixed letters; the gamepad (D8) ships after it, each with its part of D9.
- 2026-11-07 — No analytics for remapping or gamepad use for now: event names are permanent, so one is added only when it will be used.

## Steps

### Phase A — An engine that runs without a browser

No behaviour changes. Verify by playing every chamber in `npm run dev` and hearing each sound at the right moment: blue and orange portal, error (missed shot, or Space on a switch while carrying), box pick-up, fizzler, portal crossing, door and exit open and close, button press and release, switch.

- [x] **A1. Move today's rules into `src/game/classic/`** (decided, see Decisions made). Move `state.ts`, `chamber.ts`, `gateway.ts`, `portal.ts`, `subject.ts`, `wall.ts`, `floor.ts`, `laser_direction.ts` and every element file (`arrow`, `barrier`, `box`, `button`, `ditch`, `door`, `exit`, `fizzler`, `laser`, `switch`). `chamber_data.ts` and `direction.ts` stay shared; `level.ts`, `renderer.ts`, `input.ts`, `sound.ts`, `music.ts`, `audio_sources.ts` and `chamber_preview.ts` stay as the browser side. Update imports only. Verify: `npm run lint:fix`, `npm run build`, play one chamber.
- [x] **A2. Key names out of `Input`.** `state.ts` imports the `Input` class only for its key constants, which pulls DOM types into the rules. Add a `GameKey` string union with a const object (`up`, `down`, `left`, `right`, `blue`, `orange`, `interact`, `turn`) in its own file. `Input` maps `keyCode` to `GameKey`, and the rules' input reader takes `GameKey`. `Level`'s clock-start list uses the same names. Verify: build; play, including Ctrl-turn and the arrow tiles.
- [x] **A3. Rules emit events instead of playing sounds.** Add a `GameEvent` union naming each thing that happens today (portal opened blue or orange, refused, box picked up, fizzled, crossed, door opened or closed, exit opened or closed, button pressed or released, switch used). `State` collects them during `update`, and elements emit through the chamber (it already holds the gateway; give it an emit function too). Keep every emit at the exact call site and order of today's `Sound.*.play()` calls in `classic/state.ts`, `button.ts`, `switch.ts`, `door.ts` and `exit.ts`. `Level` plays the matching `Sound` for each event after the frame's update. Verify: the sound checklist above.
- [x] **A4. Counters move to `Level`.** `Level` counts portals placed from the portal-opened events (today `State.placedPortals`), so the rules' state holds no run statistics. Moves are already counted in `Level`. Verify: the analytics payloads in dev (log them) match today's for a known run.
- [x] **A5. Lint guard for the rules.** In `eslint.config.js`, for `src/game/classic/**` (later `src/game/rules/**`): forbid importing `@/game/sound`, `@/game/music`, `@/game/audio_sources`, `@/game/renderer`, `@/game/input` and `@/game/level`, and forbid the globals `window`, `document`, `Audio`, `requestAnimationFrame` and `performance`. Verify: `npm run lint` passes; adding a test import of `sound` in a rules file fails it (then remove it).
- [x] **A6. Node runner and a scripts project** (decided, see Decisions made). Add the runner as a dev dependency. Add `tsconfig.scripts.json` (Node types, no DOM lib, `paths` for `@/*`, `strict`, `noUncheckedIndexedAccess`, include `scripts/**/*.ts`) and reference it from `tsconfig.json`, so `vue-tsc --build` type-checks scripts and the rules they import. A rules file that touches the DOM then fails the build. Give `scripts/**/*.ts` Node globals in the lint config. Verify: `npm run build` and `npm run lint` pass.
- [x] **A7. Smoke script.** Add `scripts/smoke_engine.ts`: for each chamber JSON, build the classic state, run 100 empty frames and print OK. Add an npm script for it. Verify: it passes under Node.
- [ ] **A8. Audio players created lazily: only if needed.** Once the rules import no sounds, nothing on the Node path creates audio players, so this is optional. If it's ever needed, `useAudioFile` must remember each downloaded copy by address so that players created later still use it (the loading screen's handover in `asset_preloader.ts`). Verify: no extra audio requests in the Network tab after loading.
- [x] **A9. Docs.** In AGENTS.md: the layout (`src/game/classic/`, `scripts/`), the game/Vue boundary (rules emit events and `Level` plays the sounds), the third TypeScript project, and the new lint guard. Verify: re-read against the code.

### Phase B — Today's rules as a step function, and replays

- [x] **B1. State snapshot and hash.** In `src/game/classic/`, a function reading every mutable field into a plain object, in a fixed order: subject x, y, facing and carried box (as a box index); each portal's tile and side; each box's x, y; each button's pressed flag; every linkable element's `blocked` flag (barriers, ditches, doors, fizzlers, lasers, exit); the inside-a-fizzler flag; the completed flag. Add a stable text form and a 32-bit FNV-1a hash of it. Verify: the smoke script prints each chamber's start hash; two runs print the same values.
- [x] **B2. The settle step.** `stepClassic(state, frameInput)`: run one frame with the input, then run empty frames until the snapshot stops changing (a cap of 8 frames, then throw). The frame input is the set of keys pressed that frame plus whether the turn key is held. Compare snapshots, not the frame's "changed" result, which misses a fizzler firing on a later frame. Verify: the random walk in B9.
- [x] **B3. Frame log in `Level`.** For every frame with at least one key pressed, record the empty frames since the last recorded frame (capped at the settle cap, beyond which the state is settled), the keys pressed and whether the turn key is held. Today's input can press two keys in one frame, and a key can come a frame before the previous one settled, so recording whole frames with their gaps is what reproduces live play exactly. Expose it as a read-only `replay` on `Level`. Verify: log a short run's replay in dev.
- [x] **B4. Replay format.** A `ReplayData` type in `src/game/`: `format: 1`, `ruleset: 'classic'`, `chamberHash` (hash of the chamber JSON text, so an edited chamber invalidates its solution), `frames` (compact strings such as `"2:up"` or `"0:up+blue"`, with `^` marking the turn key held), and `expected` (completed, moves, portals, final hash). The screen adds the permanent `chamberId` when saving, because the game can't import the catalogue. Verify: type-checks; the file in B6 parses into it without a cast.
- [x] **B5. Replay runner.** Pure `runReplay(chamberData, replay)`: runs the frames with their gaps through the classic rules (gap empty frames, then the key frame), then settles, and returns completed, moves, portals, the final hash and the hash after each key frame. Verify: a replay logged in B3 reproduces the live run's final hash (compare it with a hash logged from the live state).
- [x] **B6. Saving a solution in development** (open decision 9). Dev builds (`import.meta.env.DEV`) get a "Download solution" button in `completion_dialog.vue` that saves `chamber_N.solution.json` (the chamber's file name), including the permanent id. The UI change uses the `frontend-design` skill even though it is dev only. Verify: the button is missing from `npm run build` output (grep `dist/`); the downloaded file replays to completion.
- [x] **B7. Record a solution for every chamber.** Commit them as `src/chambers/chamber_N.solution.json` next to each chamber (not imported by the app, so not bundled). Verify: B8 passes.
- [x] **B8. Local replay check.** `scripts/check_replays.ts` plus an npm script: for every chamber in the catalogue, load its solution, check the chamber hash, replay, and compare with `expected`. Print one line per chamber and exit non-zero on any failure. Add it to stage 00's local check command. Verify: passes; editing one step of a solution makes it fail.
- [x] **B9. Random walk check.** `scripts/random_walk.ts`: seeded random frame inputs (100,000 per chamber) through `stepClassic`. It must never hit the settle cap or throw, and it reports steps per second as the baseline for stage 02. Verify: passes; the numbers go into "Notes for later stages".
- [x] **B10. Behaviour fixtures.** Record short replays that pin today's odd behaviour, each with its expected final hash: coming out of a portal onto an open ditch, onto an active laser and onto a closed exit (which completes the chamber); a fizzler firing a frame late after a portal; a button releasing behind a carried box. The box-button crash needs a tiny fixture chamber, because no real chamber triggers it. Keep fixtures in `scripts/fixtures/`, outside the catalogue. The replay check runs them too. Verify: they pass on classic. Phase F uses them as evidence for each intended change.
- [x] **B11. Docs.** In AGENTS.md: the solution files (what they are, when to re-record), the replay check in the local checks, and the "No test suite" rule now naming replays as part of the safety net.

### Phase C — Undo and redo (on today's engine, open decision 2)

- [x] **C2. History in `Level`.** Before each key frame that changes the snapshot, push the snapshot onto an undo stack; a new change clears the redo stack. Inputs that change nothing (Ctrl alone, walking into a wall already facing it) add no entry. ### Phase D — Input rewrite

- [ ] **D1. Actions and bindings.** In `src/game/`: an `InputAction` union (up, down, left, right, turn (held), blue, orange, interact, undo, redo) and an `InputBindings` type (action → one key, a `KeyboardEvent.code` with left/right modifier pairs folded into one), with defaults that match today's keys (decided, see Decisions made). `Input` takes bindings and maps `event.code` to actions. Verify: play with the defaults.
- [ ] **D2. An ordered press queue.** Replace the per-frame key set with a queue of presses in arrival order, each recording whether the turn key was held at that moment. Auto-repeat is kept (holding an arrow walks), but a repeat is dropped while an earlier press of the same key is still waiting. `Level` takes the next press only once the state has settled (open decision 7), so two keys in one frame both count, in the order pressed. This replaces today's single arrow per frame, the A-beats-D rule and move-then-shoot; note it as an intended change for phase F. Verify: press an arrow and A at the same moment in both orders and get both orders' results; replays still pass (they replay frames, not the queue).
- [ ] **D3. Browser defaults.** Call `preventDefault` only while playing, and only for bound keys that have a browser default (arrows, Space, and any bound key that scrolls or activates). Never for Escape, Tab, F-keys, or combinations with Alt or Meta. Verify: Tab and Escape still work; the page never scrolls during play.
- [ ] **D4. Key labels.** A helper that turns a `code` into the label printed on the player's keyboard, using `navigator.keyboard.getLayoutMap()` where it exists and a built-in US table otherwise. Verify: in Chromium with an AZERTY layout, the legend shows the AZERTY letters.
- [ ] **D5. Saved bindings.** A service (next to the settings service, or inside it) stores `portal-2d.key-bindings` as JSON, with `try`/`catch` per AGENTS.md. It validates on read: an unknown action or code, or a duplicate, falls back to that action's default. It has a reset to defaults and passes the bindings into `Level` through `chamber_screen.vue` (the game can't read `localStorage`). Verify: change a binding, reload, and it's kept; corrupt the stored JSON by hand and the defaults return.
- [ ] **D6. Controls settings UI.** Under Settings, a "Controls" row that opens a third column listing each action with its key caps. Enter or a click starts rebinding and captures the next key; Escape cancels; Escape, Tab, Alt, Meta and the F-keys can't be bound; a key already in use is swapped. A final "Reset controls" row. Use the `frontend-design` skill and follow the home-menu keyboard rules in AGENTS.md (Right or Enter steps in, Left or Escape steps back, one Tab stop per column). Verify: the whole flow by keyboard only, then by mouse.
- [ ] **D7. Legend from bindings.** `chamber_legend.vue` shows the bound keys' labels instead of fixed caps. Verify: rebind A to Q and the legend says Q.
- [ ] **D8. Gamepad bridge** (open decision 8). A service polls `navigator.getGamepads()` on animation frames, with a dead zone for the stick and repeat for held directions, and turns the standard mapping into actions. In a chamber: D-pad or left stick move, X blue portal, B orange portal, A interact, LB held turn, Y undo, RB redo, Start pause (Escape). In menus and dialogs: D-pad moves, A is Enter, B is Escape. It knows whether a chamber is being played from the route. Verify: a full chamber and the menus with a pad only; nothing happens with no pad connected.
- [ ] **D9. Docs and changelog.** AGENTS.md: keyboard ownership (bindings, queue, browser defaults, gamepad), persistence (the bindings key), and the Settings column. A changelog release ("Change the controls", "Play with a gamepad"). Verify: re-read against the code.

### Phase E — v2 rules

Write the rules down first, build the comparison tool, then port one element at a time.

- [ ] **E1. Write the v2 rules.** In `docs/elements.md`, a "Rules" section: the order inside a step (turn or move or portal crossing → enterability → carried box follows → landing effects → buttons → link effects, repeated until nothing changes, with a cap → fizzler rule → exit check), what each element does, and the defined behaviour for every inherited bug (open decisions 11–13, 15) and for a laser or ditch turning on under the subject (recommended: nothing happens, you can walk off). Verify: read it against `src/game/classic/state.ts` line by line; every difference is either a listed fix or a mistake.
- [ ] **E2. Comparison tool.** `scripts/compare_engines.ts`: runs the same inputs through classic (`stepClassic`) and v2, and after each input compares a shared view (subject, portals, boxes, buttons, open flags, completed). Each intended difference is listed in code with a short id, a description and a check that recognises its situation (for example, "classic crossed into a tile that can't be entered"). Any other difference fails with the step and both states. Verify: run it against classic on both sides; it passes trivially.
- [ ] **E3. Chamber format v2 types.** In `src/game/chamber_data.ts` (or a v2 file next to it): `version: number` (2); optional lists, where a missing one means empty; wall entries with an optional `takesPortals: boolean` (default true); link groups (a trigger's `links` may name a group defined once in the chamber); an optional `par` block (moves, portals), left empty here and filled by stage 02, so adding par later needs no version bump. JSON imports widen string literals to `string`, so keep **one optional list per element type**, not a single list told apart by a `type` string, which would need a cast. If practical, derive the type from the element registry (E5) with a mapped type, so a new element file extends it. Verify: a v2 JSON fixture imports and type-checks without a cast.
- [ ] **E4. Upgrade and validate.** A pure upgrader from v1 (no `version`) to v2, chained so that v2 → v3 can follow later. A pure validator, usable at load time in the browser as well as in scripts (stage 05 validates shared links with it), returning readable errors with tile positions: unknown or duplicate link ids, links to elements that can't be linked, invalid overlaps on a tile, subject or exit inside a wall, out of bounds, a chamber not enclosed (open decision 15), a box linked to a button (warning, open decision 12). Add a `scripts/check_chambers.ts` command and include it in the local checks. The chamber files stay v1 until G, because classic still reads them; v2 upgrades them at load. Verify: all three chambers upgrade and validate; a broken fixture reports each error.
- [ ] **E5. Element definitions and registry.** In `src/game/rules/`: an element definition type, one file per element type, and a registry. A definition says: its list key in the JSON, draw layer, whether it can be linked, its default open state, whether it blocks walking or shots (by open state), whether it takes portals, optional hooks (on enter, on interact, pressed-by, on link open or close), whether entering or leaving its tile can change state (stage 02's solver stops its walking shortcut on those tiles), its event names, and how it is drawn. Shape the hook list and the step order (E1) so stage 03's six needs fit later without reshaping the step (see 03's "Depends on": movement continuation, after-step update, derived state, solid movable objects, per-element counters, link actions beyond open/close); they don't have to be implemented now. Verify: build; the registry lists every element of today's game.
- [ ] **E6. Compiled chamber.** The static part, built once per load: grid size, per-cell indexes (a typed array per lookup), resolved links and groups, wall portal flags, and each box's start tile. Every lookup is O(1). Verify: lookups agree with classic's `get*` methods for every cell of every chamber (a script).
- [ ] **E7. Compact immutable state.** Subject x, y, facing and carried box index; two portals (wall cell and side, or none); box positions; button pressed bits; open bits per linkable element; completed. No counters and no fizzler flag (open decision 13). Add a key for maps (a string or byte form) and a hash. Verify: print each chamber's state size; stage 02 needs it to stay in the hundreds of bytes.
- [ ] **E8. Actions and the pure step.** `step(chamber, state, action) → {state, events}`. Actions: move up, down, left or right; turn to each direction (today's Ctrl plus arrow); blue; orange; interact. Undo and redo are not actions, they live in `Level`. Implement the order from E1 and the shot trace with today's blocking rules and portal-side rules. Verify: build. Behaviour is checked from E9 on, with the comparison tool.
- [ ] **E9. Port elements one at a time.** Order: walls and floor, portals and the shot, barrier, door, exit, ditch, laser, arrow, box, button, switch, fizzler. After each one, run the comparison tool on random walks limited to chambers or fixtures that use only the elements ported so far, and on the recorded solutions once everything is in. Verify: the comparison tool passes, apart from listed differences.
- [ ] **E10. Renderer for v2.** The renderer draws from the element definitions by layer, with today's exact drawing code, colours and sizes (the visuals stay frozen until stage 04). A dev-only page renders every state along every recorded solution with both renderers at a fixed pixel ratio and compares pixels (`getImageData`), reporting the first mismatch. Verify: zero mismatches.
- [ ] **E11. `Level` runs v2 behind a dev flag.** In dev only (`?rules=v2`), the chamber screen plays v2: input presses become actions, each fully resolved by `step` (no settling), undo and redo become a stack of immutable states, and events drive sounds, counters and completion. Verify: play every chamber with undo, remapped keys and a gamepad.
- [ ] **E12. Measure.** Steps per second under Node on random walks and state size per chamber, compared with the B9 baseline. Verify: numbers written into "Notes for later stages".

## Go/no-go points

- **After B5 and B8:** if a replay of a live run doesn't reproduce its final hash, stop. Fix the recorder (log every frame if needed) before building undo or v2 on it.
- **After B9:** if the settle step ever hits its cap, the "state stops changing" assumption is wrong somewhere. Find the loop before going on.
- **After C1:** if snapshot restore doesn't round-trip on random walks, undo on today's engine is cancelled and moves to E11 (open decision 2 flips).
- **After E3:** if the format type can't be derived from the registry without a cast, write the optional lists by hand. "A new mechanic is one file" becomes "one file plus one line in the format type".
- **During E9:** if most element types need their own hooks in the core step, the data description isn't buying much. Record that in "Notes for later stages" so stage 03 plans honestly.
- **After E12:** if v2 runs slower than classic, or a state is far above a few hundred bytes, fix it before stage 02. The solver depends on both.
- **After F2:** any unexplained difference blocks the switch-over.

## Risks

- **Three solutions don't cover everything.** The seeded random comparison (F2) and the fixtures (B10) are the cover; widen the random inputs if differences show up late.
- **Two engines at once (E–F).** Freeze rule changes on classic while v2 is built; keep E and F short.
- **The layout change for AZERTY players** (open decision 6). Their default portal key moves to a different label. The legend and settings show real labels, and remapping fixes it; mention it in the changelog.
- **Keyboard rules get more complex** (undo, remapping, a Settings column, gamepad). Update AGENTS.md in the same step as each change, not at the end.
- **Visual drift in the renderer port.** The pixel comparison (E10) must reach zero before G1.
- **Best times before and after the fixes** may not be comparable if a route relied on a bug. Check every recorded solution's route in F4; the `rules_version` parameter separates analytics.
- **Scope.** This is the largest stage. Ship C and D as soon as each is done rather than holding them for v2.

## Notes for later stages

- **Phase B as built (2026-11-06).** `Level` feeds the rules only a frame's input (keys pressed, turn held), the same thing the log records, so a recording is exact by construction. It exposes `createReplay()` rather than a raw `replay` getter: it replays the log and refuses when any key frame's hash, the moves or the portals differ from the live run (the go/no-go after B5, checked in the browser on a 126-frame run with chords, consecutive-frame presses and held turns). `runReplay` takes the frames, not a whole replay, because `createReplay` computes `expected` with it. The chamber hash is taken from the parsed chamber as JSON, since the browser never sees the file text. The scripts can't load the catalogue (it reads Vite's development flag), so they share `scripts/chamber_files.ts`, and solutions are matched to chamber files by name. Fixtures (B10) run on seven tiny chambers of their own instead of the real ones.
- **B7 solutions (2026-11-06).** Routes were planned with throwaway tools (not committed) and recorded by playing them in the browser with scripted keys and Download solution: chamber 1 takes 163 moves and 22 portals, chamber 2 97 and 16, chamber 3 121 and 28. Not optimal, so not par. For stage 02: a plain breadth-first search over single key presses found nothing in chamber 2 after 2.75 million states (49 presses deep); treating walking as free and searching over world-changing actions (shots, pick-ups, switches, buttons) reached 13 actions deep before the number of portal pairs times box positions blew up. Each chamber needs 20–40 such actions, so the solver needs stronger pruning than either.
- **B9 baseline (Node 24, this machine, 2026-11-06).** Random walk, 100,000 steps per chamber, seeds 1–3: chamber 1 about 62,000–65,000 steps per second, chamber 2 about 78,000–80,000, chamber 3 about 47,000–52,000; about 5 s for all three. A step runs one frame with keys plus empty frames until settled, comparing JSON snapshots each frame, which dominates the cost. Deepest settle seen: one changing empty frame after a key frame (about 0.01–0.04 % of steps), far below the cap of 8. Distinct states reached per walk: 42,000–54,000; no walk completed a chamber.
- **Phase C as built (2026-11-06).** Go/no-go after C1 passed: the random walk restores a snapshot every 1,000 steps, walks the 50 inputs since again and reaches the same hash (99 checks per chamber, seeds 1–3; a deliberately broken restore fails it). Speed with the checks' time left out stayed at the B9 baseline. The history (`UndoHistory` in `src/game/classic/`) is shared by `Level` and `runReplay`. It keeps **settled** states, worked out on a hidden copy of the chamber: before each key frame that changes the settled state, the settled state before it is saved. So a key pressed a frame after a step with a late effect (a button releasing behind a carried box) never makes undo land halfway through that step or replay its sound. An undo or redo frame runs instead of the rules' frame (other keys in it are dropped; undo wins), and nothing can be undone on the frame between arriving on the exit and the completion. Undo and redo are frames of their own in the replay format (`"3:undo"`), still `format: 1`, since older files stay valid. Three fixtures pin them (`undo_back_to_start`, `redo_until_a_new_step`, `undo_before_a_late_effect`). Phase F's comparison tool compares rules only, so it must skip these. In the browser, the chamber 1 solution was played to key frame 200, undone to the start and redone (canvas identical both ways, no sound), then finished; its Download solution (735 frames, 526 of them undo or redo) replays under Node to the recorded final hash.
- **Stage 02 (solver):** use `step(chamber, state, action)` and the state key from E7. Actions are the four moves, four turns, blue, orange and interact. Turns cost no moves, so for "fewest moves" they cost 0. Boxes aren't interchangeable (a box link sends each one back to its own start), so symmetry reduction must keep box identity unless a chamber has no box links. The B9 and E12 numbers are the speed budget.
- **Stage 03 (mechanics):** add an element by writing a definition (E5). Lasers that travel and bend need state derived each step (beams computed, not stored); the step's fixpoint loop (E1) is where that goes. Check the E9 note on hooks before promising "one file".
- **Stage 04 (look):** the renderer draws by element definition and layer, and step events (moved from → to, crossed a portal, fizzled) are the hooks for animation. The pixel comparison from E10 can be reused before an intentional visual change.
- **Stage 05 (creator platform):** format v2 plus the upgrader, the validator and replays tied to a chamber hash are the basis for publishing only solved chambers. Remember that JSON string literals widen (E3).
