# Stage 01 — Engine v2

Status: In progress
Last revised: 2026-11-07

## Goal

The rules become a pure, savable step: _state + one action → next state + events_. Players get unlimited undo and redo, keys they can remap, and rules without the inherited bugs. The author gets recorded solutions that are replayed by a local command on every change, element types described by data (a new mechanic is mostly one file), and a chamber format with a version number. Today's engine is kept only as a reference to prove v2 behaves the same, then deleted.

The stage ships in slices that are each useful on their own: A and B (no player change, replays exist), C (undo), D (input), then E to G (v2 replaces the old rules).

## Depends on

- **Stage 00**
  - Records keyed by permanent chamber id. Replays name chambers by permanent id.
  - The local check command. This stage adds the replay check to it.
  - The analytics events. Phase C adds an undo count next to them.
  - The high-DPI canvas fix. It changes the renderer, so it must land before the renderer is ported in E9, and the pixel comparison in E9 must run at a fixed pixel ratio.

## Decisions made

- 2026-11-06 — Remappable keys and gamepad belong here, in the input rewrite (README decision 2).
- 2026-11-06 — Today's rules are a **reference only**. Every recorded solution runs through both engines, and the differences must match the written list of intended changes. Then the old engine is deleted and all chambers run on v2 with the fixes (README decision 3).
- 2026-11-06 — All checks are local commands run on demand. No cloud CI (README decision 6).
- 2026-11-06 — The inherited rule bugs are fixed here, not in stage 00, because rules stay frozen until v2 (README decision 1).
- 2026-11-06 — Engine scripts run under Node with **tsx**, type-checked by their own `tsconfig.scripts.json` (was open decision 1; built in A6).
- 2026-11-06 — Today's rules moved early to `src/game/classic/`, and v2 will be built in `src/game/rules/` (was open decision 10; done in A1).
- 2026-11-06 — Undo lands on **today's engine**, by restoring snapshots; the restore code is deleted with the old engine (was open decision 2; built in phase C).
- 2026-11-06 — `moves` and `portals` keep counting every step, undone ones included; redo counts nothing; an `undos` count is sent with `chamber_restart`, `chamber_quit`, `chamber_abandon` and `chamber_complete`. Stage 04 picks the medal basis (was open decision 3; built in C4).
- 2026-11-06 — Reset chamber stays a full restart and clears undo and redo; undoing all the way back is the rewind, and the clock keeps running (was open decision 4; built in C6).
- 2026-11-06 — Z undoes and X redoes; remappable after phase D (was open decision 5; built in C3).
- 2026-11-06 — Solutions are saved in development with a dev-only "Download solution" button in the completion dialog, the file named after the chamber (was open decision 9; built in B6).
- 2026-11-07 — Keys are bound by physical position (`KeyboardEvent.code`), with the player's layout labels shown wherever keys appear; AZERTY players' default portal key moves to the key labelled Q (was open decision 6; built in D1 and D4).
- 2026-11-07 — Live play applies the next queued press only once the state has settled, so live play matches the step function (was open decision 7; built in D2).
- 2026-11-07 — No gamepad support: the gamepad bridge (was open decision 8, step D8) is dropped, and no other stage plans it (README decision 9).
- 2026-11-07 — One key per action. A left/right modifier pair counts as one key, so the default turn key is either Ctrl (D1, D6).
- 2026-11-07 — Escape, Tab, Alt, Meta and the F-keys can't be bound: Escape and Tab belong to the screens, Alt and Meta combinations and the F-keys to the browser (bound to turn, Alt+Left would go Back mid-chamber) (D6).
- 2026-11-07 — D1 to D7 ship as one release with D9, so binding by position never ships while the legend still shows fixed letters.
- 2026-11-07 — No analytics for remapping for now: event names are permanent, so one is added only when it will be used.
- 2026-11-07 — Coming out of a portal onto a tile you couldn't walk onto (closed door, raised barrier, open ditch, active laser, closed exit, wrong-way arrow) is refused with the error sound, like walking into it (was open decision 11; written in E1).
- 2026-11-07 — Releasing a button linked to a box does nothing to the box; the validator warns (was open decision 12; written in E1).
- 2026-11-07 — Fizzlers: whenever the subject is in an active field during a step, both portals close and a carried box is destroyed; `fizzled` is reported only on entering the field or when it turns on under the subject; no "inside a fizzler" flag in the state (was open decision 13; written in E1).
- 2026-11-07 — Outside the chamber's edge is wall, and the validator requires enclosed chambers (was open decision 15; written in E1).
- 2026-11-07 — A door, the exit, a barrier, a ditch or a laser that starts blocking under the subject does nothing to it: it can walk off, as today (written in E1).
- 2026-11-07 — An element definition holds only its draw layer: how it is drawn stays with the browser-side renderer, looked up by element kind in E10, because the rules can't touch the canvas (built in E5).
- 2026-11-07 — Element definitions hold fixed properties only; their hooks are written with the step in E8, once the compiled chamber and the state exist (built in E5).
- 2026-11-07 — The registry covers walls and the ten elements (barrier, ditch, box, button, switch, door, fizzler, exit, laser, arrow); the subject and the portals belong to the core step (built in E5).
- 2026-11-07 — Format 2's element fields are derived from the registry (the spike on barriers and the exit passed, then every list); the file reader and the validator stay hand-written (built in E5).

## Steps

### Phase A — An engine that runs without a browser

No behaviour changes. Verify by playing every chamber in `npm run dev` and hearing each sound at the right moment: blue and orange portal, error (missed shot, or Space on a switch while carrying), box pick-up, fizzler, portal crossing, door and exit open and close, button press and release, switch.

- [x] **A1. Move today's rules into `src/game/classic/`** (decided, see Decisions made). Move `state.ts`, `chamber.ts`, `gateway.ts`, `portal.ts`, `subject.ts`, `wall.ts`, `floor.ts`, `laser_direction.ts` and every element file (`arrow`, `barrier`, `box`, `button`, `ditch`, `door`, `exit`, `fizzler`, `laser`, `switch`). `chamber_data.ts` and `direction.ts` stay shared; `level.ts`, `renderer.ts`, `input.ts`, `sound.ts`, `music.ts`, `audio_sources.ts` and `chamber_preview.ts` stay as the browser side. Update imports only. Verify: `npm run lint:fix`, `npm run build`, play one chamber.
- [x] **A2. Key names out of `Input`.** `state.ts` imports the `Input` class only for its key constants, which pulls DOM types into the rules. Add a `GameKey` string union with a const object (`up`, `down`, `left`, `right`, `blue`, `orange`, `interact`, `turn`) in its own file. `Input` maps `keyCode` to `GameKey`, and the rules' input reader takes `GameKey`. `Level`'s clock-start list uses the same names. Verify: build; play, including Ctrl-turn and the arrow tiles.
- [x] **A3. Rules emit events instead of playing sounds.** Add a `GameEvent` union naming each thing that happens today (portal opened blue or orange, refused, box picked up, fizzled, crossed, door opened or closed, exit opened or closed, button pressed or released, switch used). `State` collects them during `update`, and elements emit through the chamber (it already holds the gateway; give it an emit function too). Keep every emit at the exact call site and order of today's `Sound.*.play()` calls in `classic/state.ts`, `button.ts`, `switch.ts`, `door.ts` and `exit.ts`. `Level` plays the matching `Sound` for each event after the frame's update. Verify: the sound checklist above.
- [x] **A4. Counters move to `Level`.** `Level` counts portals placed from the portal-opened events (today `State.placedPortals`), so the rules' state holds no run statistics. Moves are already counted in `Level`. Verify: the analytics payloads in dev (log them) match today's for a known run.
- [x] **A5. Lint guard for the rules.** In `eslint.config.js`, for `src/game/classic/**` (later `src/game/rules/**`): forbid importing `@/game/sound`, `@/game/music`, `@/game/audio_sources`, `@/game/renderer`, `@/game/input` and `@/game/level`, and forbid the globals `window`, `document`, `Audio`, `requestAnimationFrame` and `performance`. Add `tsconfig.scripts.json` (Node types, no DOM lib, `paths` for `@/*`, `strict`, `noUncheckedIndexedAccess`, include `scripts/**/*.ts`) and reference it from `tsconfig.json`, so `vue-tsc --build` type-checks scripts and the rules they import. A rules file that touches the DOM then fails the build. Give `scripts/**/*.ts` Node globals in the lint config. Verify: `npm run build` and `npm run lint` pass.
- [x] **A7. Smoke script.** Add `scripts/smoke_engine.ts`: for each chamber JSON, build the classic state, run 100 empty frames and print OK. Add an npm script for it. Verify: it passes under Node.
- [ ] **A8. Audio players created lazily: only if needed.** Once the rules import no sounds, nothing on the Node path creates audio players, so this is optional. If it's ever needed, `useAudioFile` must remember each downloaded copy by address so that players created later still use it (the loading screen's handover in `asset_preloader.ts`). ### Phase B — Today's rules as a step function, and replays

- [x] **B1. State snapshot and hash.** In `src/game/classic/`, a function reading every mutable field into a plain object, in a fixed order: subject x, y, facing and carried box (as a box index); each portal's tile and side; each box's x, y; each button's pressed flag; every linkable element's `blocked` flag (barriers, ditches, doors, fizzlers, lasers, exit); the inside-a-fizzler flag; the completed flag. Add a stable text form and a 32-bit FNV-1a hash of it. Verify: the smoke script prints each chamber's start hash; two runs print the same values.
- [x] **B2. The settle step.** `stepClassic(state, frameInput)`: run one frame with the input, then run empty frames until the snapshot stops changing (a cap of 8 frames, then throw). The frame input is the set of keys pressed that frame plus whether the turn key is held. Compare snapshots, not the frame's "changed" result, which misses a fizzler firing on a later frame. Verify: the random walk in B9.
- [x] **B3. Frame log in `Level`.** For every frame with at least one key pressed, record the empty frames since the last recorded frame (capped at the settle cap, beyond which the state is settled), the keys pressed and whether the turn key is held. Today's input can press two keys in one frame, and a key can come a frame before the previous one settled, so recording whole frames with their gaps is what reproduces live play exactly. Expose it as a read-only `replay` on `Level`. Verify: log a short run's replay in dev.
- [x] **B4. Replay format.** A `ReplayData` type in `src/game/`: `format: 1`, `ruleset: 'classic'`, `chamberHash` (hash of the chamber JSON text, so an edited chamber invalidates its solution), `frames` (compact strings such as `"2:up"` or `"0:up+blue"`, with `^` marking the turn key held), and `expected` (completed, moves, portals, final hash). The screen adds the permanent `chamberId` when saving, because the game can't import the catalogue. Verify: type-checks; the file in B6 parses into it without a cast.
- [x] **B5. Replay runner.** Pure `runReplay(chamberData, replay)`: runs the frames with their gaps through the classic rules (gap empty frames, then the key frame), then settles, and returns completed, moves, portals, the final hash and the hash after each key frame. Verify: a replay logged in B3 reproduces the live run's final hash (compare it with a hash logged from the live state).
- [x] **B6. Saving a solution in development** (open decision 9). Dev builds (`import.meta.env.DEV`) get a "Download solution" button in `completion_dialog.vue` that saves `chamber_N.solution.json` (the chamber's file name), including the permanent id. The UI change uses the `frontend-design` skill even though it is dev only. Verify: the button is missing from `npm run build` output (grep `dist/`); the downloaded file replays to completion.
- [x] **B7. Record a solution for every chamber.** Commit them as `src/chambers/chamber_N.solution.json` next to each chamber (not imported by the app, so not bundled). Verify: B8 passes.
- [x] **B8. Local replay check.** `scripts/check_replays.ts` plus an npm script: for every chamber in the catalogue, load its solution, check the chamber hash, replay, and compare with `expected`. Print one line per chamber and exit non-zero on any failure. Add it to stage 00's local check command. Verify: passes; editing one step of a solution makes it fail.
- [x] **B9. Random walk check.** `scripts/random_walk.ts`: seeded random frame inputs (100,000 per chamber) through `stepClassic`. It must never hit the settle cap or throw, and it reports steps per second as the baseline for stage 02. Verify: passes; the numbers go into "Notes for later stages".
- [x] **B10. Behaviour fixtures.** Record short replays that pin today's odd behaviour, each with its expected final hash: coming out of a portal onto an open ditch, onto an active laser and onto a closed exit (which completes the chamber); a fizzler firing a frame late after a portal; a button releasing behind a carried box. The box-button crash needs a tiny fixture chamber, because no real chamber triggers it. Keep fixtures in `scripts/fixtures/`, outside the catalogue. The replay check runs them too. Verify: they pass on classic. Phase F uses them as evidence for each intended change.
- [x] **B11. Docs.** In AGENTS.md: the solution files (what they are, when to re-record), the replay check in the local checks, and the "No test suite" rule now naming replays as part of the safety net.

### Phase C — Undo and redo (on today's engine, open decision 2)

### Phase D — Input rewrite

- [x] **D1. Actions and bindings.** In `src/game/`: an `InputAction` union (up, down, left, right, turn (held), blue, orange, interact, undo, redo) and an `InputBindings` type (action → one key, a `KeyboardEvent.code` with left/right modifier pairs folded into one), with defaults that match today's keys (decided, see Decisions made). `Input` takes bindings and maps `event.code` to actions. Verify: play with the defaults.
- [x] **D2. An ordered press queue.** Replace the per-frame key set with a queue of presses in arrival order, each recording whether the turn key was held at that moment. Auto-repeat is kept (holding an arrow walks), but a repeat is dropped while an earlier press of the same key is still waiting. `Level` takes the next press only once the state has settled (open decision 7), so two keys in one frame both count, in the order pressed. This replaces today's single arrow per frame, the A-beats-D rule and move-then-shoot; note it as an intended change for phase F. Verify: press an arrow and A at the same moment in both orders and get both orders' results; replays still pass (they replay frames, not the queue).
- [x] **D3. Browser defaults.** Call `preventDefault` only while playing, and only for bound keys that have a browser default (arrows, Space, and any bound key that scrolls or activates). Never for Escape, Tab, F-keys, or combinations with Alt or Meta. Verify: Tab and Escape still work; the page never scrolls during play.
- [x] **D4. Key labels.** A helper that turns a `code` into the label printed on the player's keyboard, using `navigator.keyboard.getLayoutMap()` where it exists and a built-in US table otherwise. Verify: in Chromium with an AZERTY layout, the legend shows the AZERTY letters.
- [x] **D5. Saved bindings.** A service (next to the settings service, or inside it) stores `portal-2d.key-bindings` as JSON, with `try`/`catch` per AGENTS.md. It validates on read: an unknown action or code, or a duplicate, falls back to that action's default. It has a reset to defaults and passes the bindings into `Level` through `chamber_screen.vue` (the game can't read `localStorage`). Verify: change a binding, reload, and it's kept; corrupt the stored JSON by hand and the defaults return.
- [x] **D6. Controls settings UI.** Under Settings, a "Controls" row that opens a third column listing each action with its key caps. Enter or a click starts rebinding and captures the next key; Escape cancels; Escape, Tab, Alt, Meta and the F-keys can't be bound; a key already in use is swapped. A final "Reset controls" row. Use the `frontend-design` skill and follow the home-menu keyboard rules in AGENTS.md (Right or Enter steps in, Left or Escape steps back, one Tab stop per column). Verify: the whole flow by keyboard only, then by mouse.
- [x] **D7. Legend from bindings.** `chamber_legend.vue` shows the bound keys' labels instead of fixed caps. Verify: rebind A to Q and the legend says Q.
- [x] **D9. Docs and changelog.** AGENTS.md: keyboard ownership (bindings, queue, browser defaults), persistence (the bindings key), and the Settings column. A changelog release ("Change the controls"). Verify: re-read against the code.

### Phase E — v2 rules

Write the rules down first, build the comparison tool, then port one element at a time.

- [x] **E1. Write the v2 rules.** In `docs/elements.md`, a "Rules" section: the order inside a step (turn or move or portal crossing → enterability → carried box follows → landing effects → buttons → link effects, repeated until nothing changes, with a cap → fizzler rule → exit check), what each element does, and the defined behaviour for every inherited bug (open decisions 11–13, 15) and for a laser or ditch turning on under the subject (recommended: nothing happens, you can walk off). Verify: read it against `src/game/classic/state.ts` line by line; every difference is either a listed fix or a mistake.
- [x] **E2. Comparison tool.** `scripts/compare_engines.ts`: runs the same inputs through classic (`stepClassic`) and v2, and after each input compares a shared view (subject, portals, boxes, buttons, open flags, completed). Each intended difference is listed in code with a short id, a description and a check that recognises its situation (for example, "classic crossed into a tile that can't be entered"). Any other difference fails with the step and both states. Verify: run it against classic on both sides; it passes trivially.
- [x] **E3. Chamber format v2 types.** In `src/game/chamber_data.ts` (or a v2 file next to it): `version: number` (2); optional lists, where a missing one means empty; wall entries with an optional `takesPortals: boolean` (default true); link groups (a trigger's `links` may name a group defined once in the chamber); an optional `par` block (moves, portals), left empty here and filled by stage 02, so adding par later needs no version bump. JSON imports widen string literals to `string`, so keep **one optional list per element type**, not a single list told apart by a `type` string, which would need a cast. If practical, derive the type from the element registry (E5) with a mapped type, so a new element file extends it. Verify: a v2 JSON fixture imports and type-checks without a cast.
- [x] **E4. Upgrade and validate.** A pure upgrader from v1 (no `version`) to v2, chained so that v2 → v3 can follow later. A pure validator, usable at load time in the browser as well as in scripts (stage 05 validates shared links with it), returning readable errors with tile positions: unknown or duplicate link ids, links to elements that can't be linked, invalid overlaps on a tile, subject or exit inside a wall, out of bounds, a chamber not enclosed (open decision 15), a box linked to a button (warning, open decision 12), an unknown or misspelled field (type checking can't catch one in an imported file), a group naming another group. Add a `scripts/check_chambers.ts` command and include it in the local checks. The chamber files stay v1 until G, because classic still reads them; v2 upgrades them at load. Verify: all three chambers upgrade and validate; a broken fixture reports each error.
- [x] **E5. Element definitions and registry.** In `src/game/rules/`: an element definition type, one file per element type (`elements/`), and a registry (decided, see Decisions made). A definition holds fixed data only: its field in the JSON and whether that is one entry or a list, which tiles it sits on, its draw layer, whether it can be linked, its default blocked state, when it blocks walking (never, when blocked, always, or unless moving its way) and shots, whether standing on it stops shooting, whether it takes portals, whether entering or leaving its tile can change state (stage 02's solver stops its walking shortcut on those tiles), and its event names. How it is drawn stays with the renderer (E10), and its hooks come with the step (E8). Format 2's element fields are derived from the registry. Verify: build; `npm run chamber:check` confirms the registry holds every element of today's game, the parser accepts each one's field, and every event has one owner.
- [ ] **E6. Compiled chamber.** The static part, built once per load: grid size, per-cell indexes (a typed array per lookup), resolved links and groups, wall portal flags, and each box's start tile. Every lookup is O(1). Verify: lookups agree with classic's `get*` methods for every cell of every chamber (a script).
- [ ] **E7. Compact immutable state.** Subject x, y, facing and carried box index; two portals (wall cell and side, or none); box positions; button pressed bits; open bits per linkable element; completed. No counters and no fizzler flag (open decision 13). Add a key for maps (a string or byte form) and a hash. Verify: print each chamber's state size; stage 02 needs it to stay in the hundreds of bytes.
- [ ] **E8. Actions and the pure step.** `step(chamber, state, action) → {state, events}`. Actions: move up, down, left or right; turn to each direction (today's Ctrl plus arrow); blue; orange; interact. Undo and redo are not actions, they live in `Level`. Implement the order from E1 and the shot trace with today's blocking rules and portal-side rules, reading what blocks walking and shots from the element definitions (E5). Add the element hooks here (decided, see Decisions made): on enter, on interact, pressed-by, on link unblock or block, including what E5's fixed data can't say: a barrier rising closes a portal on its tile, a link sends a box back to its start, a switch refuses while the subject carries a box. Shape the hook list and the step order (E1) so stage 03's six needs fit later without reshaping the step (see 03's "Depends on": movement continuation, after-step update, derived state, solid movable objects, per-element counters, link actions beyond open/close); they don't have to be implemented now. Verify: build. Behaviour is checked from E9 on, with the comparison tool.
- [ ] **E9. Port elements one at a time.** Order: walls and floor, portals and the shot, barrier, door, exit, ditch, laser, arrow, box, button, switch, fizzler. After each one, run the comparison tool on random walks limited to chambers or fixtures that use only the elements ported so far, and on the recorded solutions once everything is in. Verify: the comparison tool passes, apart from listed differences.
- [ ] **E10. Renderer for v2.** The renderer draws from the element definitions by layer (`DRAW_LAYERS`, and registry order inside a layer), with today's exact drawing code, colours and sizes (the visuals stay frozen until stage 04). The drawing code stays on the browser side, looked up by element kind (decided, see Decisions made). A dev-only page renders every state along every recorded solution with both renderers at a fixed pixel ratio and compares pixels (`getImageData`), reporting the first mismatch. Verify: zero mismatches.
- [ ] **E11. `Level` runs v2 behind a dev flag.** In dev only (`?rules=v2`), the chamber screen plays v2: input presses become actions, each fully resolved by `step` (no settling), undo and redo become a stack of immutable states, and events drive sounds, counters and completion. Verify: play every chamber with undo and remapped keys.
- [ ] **E12. Measure.** Steps per second under Node on random walks and state size per chamber, compared with the B9 baseline. Verify: numbers written into "Notes for later stages".

## Go/no-go points

- **After B5 and B8:** if a replay of a live run doesn't reproduce its final hash, stop. Fix the recorder (log every frame if needed) before building undo or v2 on it.
- **After B9:** if the settle step ever hits its cap, the "state stops changing" assumption is wrong somewhere. Find the loop before going on.
- **After C1:** if snapshot restore doesn't round-trip on random walks, undo on today's engine is cancelled and moves to E11 (open decision 2 flips).
- **After E3 (checked in E5):** if the format type can't be derived from the registry without a cast, write the optional lists by hand. "A new mechanic is one file" becomes "one file plus one line in the format type". Result (2026-11-07): passed, the element fields are derived without a cast; but the file reader and the validator still list elements by hand (see "E5 as built").
- **During E9:** if most element types need their own hooks in the core step, the data description isn't buying much. Record that in "Notes for later stages" so stage 03 plans honestly.
- **After E12:** if v2 runs slower than classic, or a state is far above a few hundred bytes, fix it before stage 02. The solver depends on both.
- **After F2:** any unexplained difference blocks the switch-over.

## Risks

- **Three solutions don't cover everything.** The seeded random comparison (F2) and the fixtures (B10) are the cover; widen the random inputs if differences show up late.
- **Two engines at once (E–F).** Freeze rule changes on classic while v2 is built; keep E and F short.
- **The layout change for AZERTY players** (open decision 6). Their default portal key moves to a different label. The legend and settings show real labels, and remapping fixes it; mention it in the changelog.
- **Keyboard rules get more complex** (undo, remapping, a Settings column). Update AGENTS.md in the same step as each change, not at the end.
- **Visual drift in the renderer port.** The pixel comparison (E10) must reach zero before G1.
- **Best times before and after the fixes** may not be comparable if a route relied on a bug. Check every recorded solution's route in F4; the `rules_version` parameter separates analytics.
- **Scope.** This is the largest stage. Ship C and D as soon as each is done rather than holding them for v2.

## Notes for later stages

- **Phase B as built (2026-11-06).** `Level` feeds the rules only a frame's input (keys pressed, turn held), the same thing the log records, so a recording is exact by construction. It exposes `createReplay()` rather than a raw `replay` getter: it replays the log and refuses when any key frame's hash, the moves or the portals differ from the live run (the go/no-go after B5, checked in the browser on a 126-frame run with chords, consecutive-frame presses and held turns). `runReplay` takes the frames, not a whole replay, because `createReplay` computes `expected` with it. The chamber hash is taken from the parsed chamber as JSON, since the browser never sees the file text. The scripts can't load the catalogue (it reads Vite's development flag), so they share `scripts/chamber_files.ts`, and solutions are matched to chamber files by name. Fixtures (B10) run on seven tiny chambers of their own instead of the real ones.
- **B7 solutions (2026-11-06).** Routes were planned with throwaway tools (not committed) and recorded by playing them in the browser with scripted keys and Download solution: chamber 1 takes 163 moves and 22 portals, chamber 2 97 and 16, chamber 3 121 and 28. Not optimal, so not par. For stage 02: a plain breadth-first search over single key presses found nothing in chamber 2 after 2.75 million states (49 presses deep); treating walking as free and searching over world-changing actions (shots, pick-ups, switches, buttons) reached 13 actions deep before the number of portal pairs times box positions blew up. Each chamber needs 20–40 such actions, so the solver needs stronger pruning than either.
- **B9 baseline (Node 24, this machine, 2026-11-06).** Random walk, 100,000 steps per chamber, seeds 1–3: chamber 1 about 62,000–65,000 steps per second, chamber 2 about 78,000–80,000, chamber 3 about 47,000–52,000; about 5 s for all three. A step runs one frame with keys plus empty frames until settled, comparing JSON snapshots each frame, which dominates the cost. Deepest settle seen: one changing empty frame after a key frame (about 0.01–0.04 % of steps), far below the cap of 8. Distinct states reached per walk: 42,000–54,000; no walk completed a chamber.
- **Phase C as built (2026-11-06).** Go/no-go after C1 passed: the random walk restores a snapshot every 1,000 steps, walks the 50 inputs since again and reaches the same hash (99 checks per chamber, seeds 1–3; a deliberately broken restore fails it). Speed with the checks' time left out stayed at the B9 baseline. The history (`UndoHistory` in `src/game/classic/`) is shared by `Level` and `runReplay`. It keeps **settled** states, worked out on a hidden copy of the chamber: before each key frame that changes the settled state, the settled state before it is saved. So a key pressed a frame after a step with a late effect (a button releasing behind a carried box) never makes undo land halfway through that step or replay its sound. An undo or redo frame runs instead of the rules' frame (other keys in it are dropped; undo wins), and nothing can be undone on the frame between arriving on the exit and the completion. Undo and redo are frames of their own in the replay format (`"3:undo"`), still `format: 1`, since older files stay valid. Three fixtures pin them (`undo_back_to_start`, `redo_until_a_new_step`, `undo_before_a_late_effect`). Phase F's comparison tool compares rules only, so it must skip these. In the browser, the chamber 1 solution was played to key frame 200, undone to the start and redone (canvas identical both ways, no sound), then finished; its Download solution (735 frames, 526 of them undo or redo) replays under Node to the recorded final hash.
- **Phase D keyboard as built (2026-11-07).** The game keys (`GameKey`) already are the actions D1 names, so there is no second union; `KeyBindings` (`src/game/key_bindings.ts`) holds one key per game key, a `KeyboardEvent.code` with left and right Ctrl and Shift folded into `Control` and `Shift`. `Input` queues presses and `Level` takes one only after a frame that changed nothing, so a step that changes the state takes two frames (the key frame and one quiet frame), while an undo or a press that changes nothing takes one. Live play now never puts two keys in one frame, so today's single arrow per frame, A beating D and move-then-shoot are reachable only through replays; none of the three recorded solutions has a two-key frame. Phase F lists it as an intended change. The replay format is unchanged.
- **E1 as written (2026-11-07).** The rules are in `docs/elements.md` under "Rules (v2)", with a first list of changes and their ids for the comparison tool (E2). A chamber's start is settled at load (the repeat loop and the exit check once, with no action), as today's frame loop does before the first key, so E7, E8 and the comparison tool start from that state. Four refinements of E1's sketch: the fizzler rule runs inside the repeat loop, before the buttons, so a box it sends back to a start tile on a button presses it in the same step (after the loop, that would be a new one-step delay), and there is no separate landing effect; the exit check doesn't ask whether the exit is open, since only an open exit can be entered, so arriving as it closes still completes, as today; a turn towards the way the subject already faces is a move, as today (E8's turn actions must follow it); and a link to a carried box does nothing, today's net effect. Judging buttons only after the carried box has moved can change a settled result, not just timing: today the button a carried box leaves always releases last, so two buttons sharing a link can end differently (listed under `no_late_effects`). Bug 4 (the fizzler flag), several keys in one frame, a carried box's link, the edge, keys after completion and that button order have no fixture, so E2 needs its own cases for them.
- **E2 as built (2026-11-07).** `npm run compare:engines` (`scripts/compare_engines.ts`, with `scripts/engine_comparison/`) plays each chamber's solution and a seeded random walk one settled step at a time on two engines behind one small interface (start a chamber settled, take an action, read the state, take over a state) and compares the state and the events after every step. Today's rules stand in for v2 until E8 replaces the stand-in in `compare_engines.ts`. An excused difference is counted by id, then today's rules take over v2's state (the "inside a fizzler" flag set when the subject stands in an active field). A self-test plays the seven fixtures that work one key at a time and requires exactly their own id at their step; it catches a check that stops recognising its fixture, not one that grows too broad. Three fixtures were added for it (`carried_box_button_released_last`, `fizzler_flag_kept_across_switched_off_fizzler`, `walk_out_through_the_edge`); the last one's chamber is open at the edge, so v2's validator (E4) will reject it, and F1 must play it without validating. One-action-per-step, keys after completion and the timing half of `no_late_effects` have no check yet: they need frame-by-frame replays (F1). With a stand-in that refuses blocked crossings, 300,000 random steps on each of seeds 1–3 never met that situation, so F2's evidence for the listed changes will come from the fixtures more than from random walks. It takes about 12 s on this machine.
- **E3 as built (2026-11-07).** `ChamberDataV2` in `src/game/chamber_data_v2.ts`, beside today's format, reusing its element shapes; G2 makes it `ChamberData`. `version` is typed `number`, because an imported file reads `2` as one; the validator checks the value. Link groups take their id from the same pool as elements, so a trigger's `links` names a group like an element; a group holds element ids only. `par` holds optional `moves` and `portals`. The optional lists are written by hand: the registry they could be derived from arrives in E5, which should try it (the go/no-go after E3 moves there). `scripts/fixtures/format_examples.ts` types `format_v2_example.json`, which uses every addition and leaves most lists out; the build failed on it with `takesPortals` as text, a door missing `y` and no `version`. Type checking doesn't catch an unknown or misspelled field in an imported file, so E4's validator must.
- **E4 as built (2026-11-07).** `loadChamber` (`src/game/rules/load_chamber.ts`) takes raw JSON: the upgrade chain (`upgrade_chamber.ts`, one step per format version; format 1 has no `version`, and its id of 0, which meant no id, is removed), then a field-by-field reader that builds a typed `ChamberDataV2` without a cast (`chamber_parser.ts`), then the layout checks (`validate_chamber.ts`). Each step runs only when the one before found no error, so a file with wrong fields reports no layout problems until they are fixed. Overlaps are strict: a wall holds at most one barrier; a floor tile holds at most one fixed element, except two crossing lasers (chamber 1 has one such pair); a box and the subject start on plain floor or a button. Stage 03's interaction table can loosen them cell by cell. "Enclosed" means every edge tile holds a wall, a barrier, a door or the exit. Chamber 1 held a stray barrier at (-2, 2), outside the chamber, so it was removed and the chamber's solution regenerated by replaying the same keys on the edited file (same moves and portals, new chamber and final hashes). The browser-free lint guard and the scripts' TypeScript project now cover `src/game/rules/`. `npm run chamber:check` loads the three chambers and six pinned cases (the format 2 example, a format 1 file with an id of 0, a newer format, a file that isn't an object, and one broken file for wrong fields and one for a wrong layout).
- **E5 as built (2026-11-07).** `src/game/rules/element_definition.ts` (the type and `defineElement`), `draw_layer.ts`, one file per element in `elements/`, and `element_registry.ts` (`ELEMENT_REGISTRY` in today's drawing order, `ElementKind`, `CORE_STEP_EVENTS` and `ChamberElementFields`). Three fields beyond E5's first sketch: `count` (the exit is one required entry, every other element a list), `sitsOn` (a barrier can sit on a wall tile) and `stopsShootingFrom` (standing in a fizzler that is on silences the portal keys). The layers are coarse (floor, floor marks, structure, blockers, portals, fixtures, items, subject, fields), with registry order inside a layer; that draws exactly as today only because the validator allows one fixed element per floor tile, which E10's pixel comparison will confirm. A definition carries its entry type as a type only (a symbol key that is never set), so `ChamberDataV2` is the version, size, subject, groups and par plus fields mapped from the registry. The spike on barriers and the exit, then every list, compiled without a cast, and a broken field in the format example still names the list, the entry and the field. The wall's entry type stays in `chamber_data_v2.ts`, a type-only import cycle with the registry. The file reader (`CHAMBER_FIELDS` and its list readers), the validator (its element kinds, fixed elements, link targets and edge rule) and the upgrader still list elements by hand, and since the lists are optional, a registry entry the reader forgets still compiles (the chamber check catches it). So a new element is still a definition, a registry line, reader and validator lines, its docs and its drawing; having the reader and the validator read the registry would remove most of that. `npm run chamber:check` now also checks the registry against the format.
- **Stage 02 (solver):** use `step(chamber, state, action)` and the state key from E7. Actions are the four moves, four turns, blue, orange and interact. Turns cost no moves, so for "fewest moves" they cost 0. Boxes aren't interchangeable (a box link sends each one back to its own start), so symmetry reduction must keep box identity unless a chamber has no box links. The B9 and E12 numbers are the speed budget.
- **Stage 03 (mechanics):** add an element by writing a definition (E5). Lasers that travel and bend need state derived each step (beams computed, not stored); the step's fixpoint loop (E1) is where that goes. Check the E9 note on hooks before promising "one file".
- **Stage 04 (look):** the renderer draws by element definition and layer, and step events (moved from → to, crossed a portal, fizzled) are the hooks for animation. The pixel comparison from E10 can be reused before an intentional visual change.
- **Stage 05 (creator platform):** format v2 plus the upgrader, the validator and replays tied to a chamber hash are the basis for publishing only solved chambers. Remember that JSON string literals widen (E3).
