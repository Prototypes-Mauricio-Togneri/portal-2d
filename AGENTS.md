## Project

Portal 2D — a desktop-only, keyboard-driven puzzle game: the player crosses grid-based test chambers using a pair of portals (Vite + Vue 3, TypeScript, Composition API with `<script setup>`, vue-router, ESLint + @stylistic + type-aware typescript-eslint via @vue/eslint-config-typescript). It is a static site on Firebase Hosting; there is no backend.

`todo/` holds the author's roadmap: an overview (`README.md`) and one file per stage (`03_look_and_sound.md` to `05_creator_platform.md`; stages 00 and 01 are done, stage 02 stopped after its prototype, and their files are removed; what stage 02 learned is in `docs/solver.md`). They are not planned work; do not build any of it unless asked, and only tick a stage's checkboxes for steps you were asked to do and finished.

and for the any-route search, a guess that leaves out most box drops, which can in an unusual layout miss a route: a carried box is put down only on an element that judges what lies on it (a button), at its start, on or next to another box, next to an element that needs free hands or destroys a carried box (a switch, a fizzler), or in front of either portal while both are open), and the macro search (a whole walk then one action as one step: from every tile a walk reaches, interact, both shots each way, once per line, and each move a walk doesn't cover, through the rules' step, but no interact or move the action filter rules out; states stored with the canonical facing; breadth first for any route, with the subject stored on its region's smallest tile, one state per region from each shot line and box drops limited, the route's counts taken from its actions; ## Rules

- **After completing code changes**: Run `npm run lint:fix` and fix remaining errors, run `npm run build` (type-checks first) and fix any failures, then run `/delta-review` before responding. `npm run verify` runs the same lint (without fixing), the build and the engine checks, and changes no tracked file: `npm run smoke:engine` (every chamber file loads with the rules under Node and settles its start, printing its state's size and hash), `npm run replay:check` (every chamber's recorded solution completes with its expected moves, portals and final hash, and then no action changes the completed chamber or reports anything; every behaviour fixture in `scripts/fixtures/fixtures.ts` ends as pinned; both routes of every solver fixture in `scripts/solver_fixtures/solver_fixtures.ts`, on its chamber loaded with the layout checks, complete with their pinned counts and final hash), `npm run solver:check` (every state along each chamber's recorded solution and 100,000 seeded random steps packs into the solver's state key and unpacks unchanged; a chamber too large for the key is refused; from every state along the recorded solutions and every state the reference search finds on the solver fixtures, each walk the walk graph allows gives through the rules' step the state the solver builds, no move it leaves out lands on a plain neighbouring tile, each turn gives the state built for that facing, each shot from each tile a walk reaches, each way and colour, gives the state the solver builds from the shot it shares with its line, each interact and move the solver skips as changing nothing (not the box drops the any-route search leaves out, a guess this doesn't check) changes nothing through the rules' step but where the subject faces, and a tile a walk reaches is in the start's region exactly when a walk from it gets back to the start; on every solver fixture the reference search and the macro search find both hand-counted pars, the macro search also finds a route in its solvable mode, every route replays to the same counts, and every state the reference search found survives the key with a key of its own), `npm run random:walk` (100,000 seeded random actions per chamber and per fixture chamber, the fixture chambers read without the layout checks, each settling within the rules' pass cap, with the speed and the state's size; `--seed=` and `--steps=` change them) and `npm run chamber:check` (every chamber file reads and validates without an error, and each case in `scripts/fixtures/format_examples.ts` reports exactly the problems pinned for it, and the compiled format 2 example reaches exactly its pinned links (its group expanded) and refuses portals on exactly its pinned walls, every chamber file, fixture chamber and the example, compiled, answers wall, no portals and no element on the ring of tiles just outside its edge, then the element registry matches the format: the parser accepts every element's field, no two elements share a field, and every game event has exactly one owner, an element or the core step, and every element that blocks only while blocked has a blocked flag); it is the whole-project check that later stages extend (`npm run check` is the fix-then-build shortcut).
- **Testing in the browser**: After code changes that can be seen or played, also test them yourself with the Chrome tool when it is connected: run `npm run dev` in the background, open a new tab and exercise the change (keys, clicks, screenshots, console). Keep the tab silent, because the user may be listening to something in another tab. The Chrome tools cannot mute a tab, so after every page load, before pressing Start, run `const play = HTMLMediaElement.prototype.play; HTMLMediaElement.prototype.play = function () { this.muted = true; return play.call(this) }` in the page: every sound effect and the music play through audio elements, and nothing plays before Start. Close the tab and stop the dev server when done, and say in the report what was tested this way and what was not.
- **Game/Vue boundary**: `src/game/` is plain TypeScript and never imports Vue, vue-router, `src/components/`, `src/services/` or `src/chambers/` (enforced in `eslint.config.js`). Screens drive it, not the other way around: `chamber_screen.vue` creates a `Level` on its canvas with the player's key bindings (a plain object, read once), sized in device pixels with the device pixel ratio (given on creation and to `resize`, refitted when the stage or the ratio changes; the renderer multiplies its fixed edge widths by the ratio, so ratio 1 draws exactly as before), calls `load` (also used for reset), `resize`, `dispose`, toggles `paused`, reads `started` and `elapsedHundredths` (the chamber clock) and `moves`, `portalsPlaced` and `undos` (for analytics), gets `onCompleted` back, and in development calls `createReplay` for the completion dialog's Download solution. `Input` queues presses in arrival order, each with whether the turn key was held as it went down (a held key's repeat is dropped while its earlier press still waits; the turn key is only read as held); a bound mouse button going down is queued as a press of its game key, like a key. Each frame `Level` takes the oldest press as one action of the rules' step (`step` in `src/game/rules/step.ts`), which carries out every consequence of the action before it returns, so live play takes one action per frame, in the order pressed; pausing forgets the presses still waiting. `Level` redraws when the state changes, and while a step is being drawn (`StepAnimation`, `src/game/step_animation.ts`: about 120 ms from the state before it to the state after it, eased out and started one frame back, so the press's own frame already shows part of it) every frame, paused or not, until a frame draws its end, which the renderer then draws exactly as the plain state; idle frames draw nothing. Part way through a step, the subject and a box it carries through it are drawn at the subject's pose (`src/game/subject_pose.ts`): a move glides one tile, and a portal crossing slides into the entry portal, facing it, then out of the exit one, each half clipped to its tile, the distance still to go rounded to whole canvas pixels; everything else, turns included, shows the state after the step at once. A load or a resize redraws at the latest frame's time, so a step being drawn never goes back. Only a rules step that changes the state starts one; every press taken ends the running one at once (a new key never waits), even a press that changes nothing; undo, redo, a load and a reset show their state at once; with `prefers-reduced-motion` (read by `Level` each time a step would start one) nothing is drawn over time. Sounds, the counters, the log and `onCompleted` stay in the frame that takes the press, and the clock is unaffected. A load settles the chamber's start and plays the sounds of its events. Undo and redo bring back immutable states from `StateHistory` (`src/game/rules/`, shared with the replay runner): each step that changes the state saves the state before it and empties redo. An undo or redo press plays no sound and doesn't start the clock. `Level` reads the completion from the state after each step and then calls `onCompleted`; once the chamber is completed nothing runs and nothing can be undone. `moves` (each step that puts the subject on another tile, a portal crossing included) and `portalsPlaced` keep counting undone steps; `undos` counts undos that took a step back, and redo counts nothing. `Level` logs every press it acts on (an action, undo or redo) and the state's hash after it, and `createReplay` replays the log with the replay runner and refuses when any hash, the moves or the portals differ from the live run. The rules (`src/game/rules/`) play no sounds: they report what happens as `GameEvent`s (portal opened, refused, box picked up, fizzled, crossed, door or exit opened or closed, button pressed or released, switch used), and after each step `Level` plays the matching `Sound` for each, in order, and counts the portals placed from them. They take actions (four moves, four turns, two shots, interact), which `Level` makes from the presses (`Input` maps the physical keys to `GameKey`s). A stricter lint block for `src/game/rules/` forbids importing `sound`, `music`, `audio_sources`, `renderer`, `input`, `level`, `tile_painter`, `element_drawings`, `step_animation` and `subject_pose`, and using `window`, `document`, `Audio`, `requestAnimationFrame` and `performance`; `tsconfig.scripts.json` type-checks the rules without the DOM. The solver (`src/solver/`) has a block of its own with the same bans, plus `@scripts/*`, Node's modules (`node:*`) and `process`, so it can also run in a Web Worker; it may import `src/game/`, never Vue, components, services or chambers. The clock starts on the first press of a move, turn, portal or interact key after a load (not undo or redo), counts only unpaused frames and skips the time a tab spent hidden. Services may import from `src/game/` (settings flips `Sound.enabled` and switches between `menuMusic`, played on the home screen and resumed where it left off, and `gameMusic`, played in a chamber and started over whenever a chamber opens, is reset or is replayed; the asset preloader hands each audio player its downloaded file through `useAudioFile` in `audio_sources.ts`). `Sound.MENU_BUTTON` and `Sound.START` are interface sounds the game never plays: components play the first on the loading screen's Start button, on dialog buttons, on every move of the home menu's highlight (keys, Tab or pointer), on opening and closing a home menu section, on stepping into and back from About's or Controls' third column (not on opening Feedback or a page, which leave the game), on settings switches (after the change, so turning sound effects off stays silent), on picking a layout under Controls (with Custom, also opening its dialog), on a custom controls row starting to wait for a key and on a key or mouse button bound, and on opening the pause menu or the reset progress confirmation, and the second when a chamber is started from the home menu. They obey the sound effects setting like every other `Sound`. Game objects are never made reactive and per-frame data never passes through a `ref`: the screen writes the timer's text straight into its element each frame. The home menu's map (`chamber_preview.ts`) draws each chamber's settled start with the same renderer.
- **Rules are pinned, drawing is frozen**: The rules are defined in `docs/elements.md` (each element, the step, and every change from the original game's rules) and pinned by the recorded solutions and the behaviour fixtures. Change a rule only when explicitly asked, and then in the same change re-record the solutions (and fixtures) it alters and update `docs/elements.md`. The drawing was translated line by line from the original JavaScript: do not change drawing, colours or sizes unless explicitly asked; they stay frozen until stage 03 reworks the chamber visuals. So far stage 03 has only added the frames part way through a step (the step animation and the subject's pose); a settled state still draws exactly as before. Its colours are the named `rgba()` colours of the palette (`src/game/palette.ts`); a few are mirrored by hand in the CSS tokens, as each entry's comment says, so change both together.
- **Keyboard ownership**: The game's `Input` owns the keys and mouse buttons bound to its game keys (`src/game/key_bindings.ts`), keys read by physical position (`KeyboardEvent.code`) so they stay in place on every layout. The player picks a layout of controls under Settings: Arrow keys, the default (the arrows, A and D (portals), Space (interact), either Ctrl (held to turn), Z (undo) and X (redo)), WASD and mouse (W, A, S and D move, the left and right mouse buttons shoot blue and orange, the rest as in Arrow keys), or Custom (their own, set in its dialog, starting from the layout in use the first time it is picked). One key or mouse button per game key, never shared; a left/right modifier pair counts as one key; Escape, Tab, Alt, Meta and the F-keys can't be bound, nor any mouse button but left and right. Held keys repeat with the key's auto-repeat. While playing, it calls `preventDefault`, on keydown and keyup, only for bound keys with a browser default (the arrows, Space, Page Up/Down, Home, End, Enter, Numpad Enter, the keys where a US keyboard has / and ', and any key that types Firefox's quick-find / or ' on the player's layout), never with Alt or Meta held; a key pressed with Alt or Meta held is left to the browser and doesn't play (it only counts as held). A bound mouse button plays anywhere in the window, going down, exactly as a key (a portal shot flies the way the subject faces, not where the click lands; it starts the clock, is logged and can be undone), but never repeats while held; unbound buttons, and clicks with Alt or Meta held, are left to the browser. While playing with the right button bound, the browser's context menu is kept closed, unless Alt or Meta is held; while a dialog is open clicks do nothing and the menu opens. Keys are shown with the label the player's layout prints (`navigator.keyboard.getLayoutMap()` in Chromium, a US keyboard elsewhere), and the arrow keys as small triangles pointing their way. The numpad's keys are keys of their own, so with NumLock off its arrows don't move the subject unless bound (the menus, which read `event.key`, still follow them). Screens own Escape. On the home screen, which has no game running, Up and Down move the highlight within the column that has the keyboard (wrapping around; in the first column they change nothing else), Right or Enter opens the highlighted section and steps into it, Left or Escape closes it again; until any chamber has been opened on this device (no chamber has an attempt in the progress, so again after Reset progress), Enter, Space or a click on Play starts the tutorial instead, with the start sound, and Right still opens the chamber list. Under About the third column follows the highlighted row (a list of pages, or the changelog); Right, Enter or a click steps into the pages or the changelog (where Up and Down scroll it), and Left or Escape steps back to the About row. Under Settings, the Controls row's third column starts level with it: Arrow keys, WASD and mouse and Custom; Right, Enter or a click steps in (on the layout in use) and Left or Escape steps back, as under About. Enter, Space or a click on a layout puts it in use; on Custom it also opens the custom controls dialog (`custom_controls_dialog.vue`): one row per game key (Turn in place, Undo and Redo hidden for now, as in the legend; their keys still work), then Done, with labels re-read from the layout as it opens. Enter, Space or a click on a key's row waits for its next key: while it waits, every keydown is taken before the dialog and the screen see it (so Ctrl and Shift can be bound), a held key's repeats are ignored, the key is bound (a game key that held it takes the old one), Escape cancels silently, and a key that can't be bound shows "Can't use" and the key's name and keeps waiting; a left or right click on the waiting row binds that mouse button, a click anywhere else cancels, the release of a taken key and the click that ends a left button just bound are kept from pressing the row again, and the rows open no context menu. Binding edits Custom. Screen-reader status lines announce the layout put in use, and the dialog's wait, refusals and binds. Arrows with Alt, Ctrl or Meta are left to the browser. Each column is one Tab stop (its highlighted row, or the changelog), and a held (repeating) Enter is ignored so it can't carry over from the previous screen. The first arrival shows only the sections, with Play highlighted and focused but not open; back from a chamber, Play is open with that chamber highlighted and focused. Hovering a row highlights it, in any column; clicking a section opens it like Enter. While any dialog is open the game is paused and its input is ignored (on the home screen, the menu ignores every key but Escape, which closes the dialog), and the dialog's buttons get the keyboard (`dialog_frame.vue`: first action focused, arrow keys and Tab move between actions, and a held (repeating) Enter or Space presses nothing, so a move key bound to one can't carry into a dialog). The loading screen's Start button takes focus once loading finishes.
- **Desktop only**: Touch-first devices (`pointer: coarse`) get the desktop-only notice instead of the app. Do not add mobile layouts or touch controls.
- **Chambers**: A chamber is a JSON file in `src/chambers/`, listed in `scripts/chamber_files.ts` (the engine scripts fail on a chamber file it doesn't list), with a recorded solution next to it, plus an entry in `src/services/chamber_catalogue.ts`: a permanent `id` (0 or more: 0 is the tutorial's, the others are given in the order chambers were created; it names the chamber's files, keys its stored progress and is sent as the analytics `chamber_id`, so changing one splits that chamber's analytics history), its layout and, optionally, a name the player sees instead of "Chamber N" in the home menu and the chamber-complete dialog (the tutorial's is "Tutorial"). Its number is its position in the list, counted from 0, derived, never typed by hand; links (`/chamber/N`), the in-memory last chamber and the `chamber_number` analytics parameter follow it. In development, an id that is not a whole number of 0 or more, or is used twice, is logged as an error. Chamber files are in format 2 (`"version": 2`, described in `docs/elements.md` under "Chamber format"): `ChamberData` (`src/game/chamber_data.ts`: a `version`, lists that may be left out, walls that may refuse portals, link groups sharing the element ids, an empty par block; its element fields are typed from the element registry in `src/game/rules/element_registry.ts`, each by its definition's entry type) must accept the JSON import without a cast, so the type checker validates every chamber file, and `scripts/fixtures/format_examples.ts` types a format 2 example the same way. Type checking can't catch a misspelled or unknown field in an imported file, so the chamber loader (`src/game/rules/load_chamber.ts`) does: it reads a file as raw JSON, refuses any `version` but 2, and rejects what `docs/elements.md` lists under "What the validator rejects". The level and the home menu's map load every chamber through it and throw on a chamber it rejects, so `npm run chamber:check`, which runs it on every chamber file, must pass.
- **Persistence**: `localStorage` keys are prefixed `portal-2d.` and every access is wrapped in `try`/`catch` (storage can be blocked). Stored: sound on/off, music on/off, the controls under `portal-2d.key-bindings` (`{layout, custom}`: the layout in use, `arrow-keys`, `wasd-mouse` or `custom`, and the Custom keys, a plain object, game key → key or mouse button (`MouseLeft`, `MouseRight`), or null until Custom is first picked; the fixed layouts' keys are never stored, so a change to them always takes effect; Custom keys are read game key by game key, a stored key that can't be bound or is already taken falls back to that game key's Arrow keys key, and if that is then taken every game key goes back to Arrow keys; a layout that isn't one, or Custom with no keys, falls back to Arrow keys; renaming a game key or a key name sends a stored binding of it back to Arrow keys; unlike the progress, it is not synced between tabs, so a tab keeps the controls it loaded until it reloads), and the progress under one versioned key, `portal-2d.progress` (`{version: 2, chambers: {<id>: {completed, bestTime, attempts}}}`, by permanent chamber id; best times in hundredths of a second, attempts counted on each opening, Restart chamber and Play again). Reset progress under Settings stores an empty record. Malformed values, unknown fields and a record of another version are ignored. Stored formats may change without a migration: a stored value that no longer reads is ignored and falls back to its default (decision 13 in `todo/README.md`: friends' saves may be reset by updates). Every save writes the whole record, so each tab takes over the record whenever another tab saves it (the `storage` event). The last chamber opened (which the home menu highlights on the way back) is kept in memory only.
- **Analytics**: `src/services/analytics.ts` sends Firebase Analytics events from production builds only (`npm run dev` sends nothing), with no consent prompt. Its config holds only `apiKey`, `projectId` and `appId`; the SDK fetches the measurement ID itself. Any failure (unsupported browser, ad blocker) silently drops events and never affects the game. Events: `chamber_start` (opened, or Play again), `chamber_restart` (Restart chamber confirmed), `chamber_quit` (Exit chamber or browser Back confirmed; not Back to menu or Next chamber after finishing, nor closing the tab), `chamber_abandon` (the page closed, reloaded or left for another site before finishing; at most once per attempt, and a lower bound, since events sent as a page goes away can be lost; a page restored from the back/forward cache carries on, so an attempt can be abandoned and later still end another way) and `chamber_complete`, each with `chamber_id`, `chamber_number` and `attempt` (the chamber's attempt count on this device, cleared by Reset progress; a restart ends attempt N and the next run is N + 1), all but `chamber_start` also with `time_ms` (the time shown), `moves` (tiles stepped onto, undone ones included) and `undos` (steps taken back with undo; redo counts nothing), and `chamber_complete` also with `portals` (portals placed, misses not counted, undone ones included), `first_completion` and `new_best` (1 or 0; after Reset progress the next completion counts as first again). Restart chamber sends no `chamber_start` of its own, so runs = `chamber_start` + `chamber_restart`; `setting_change` (`setting`: sound or music, `enabled`: on or off), `progress_reset`, `changelog_open` (stepping into the changelog, not just highlighting its row), `feedback_open` and `link_open` (`link`, `url`). Event and parameter names are permanent: renaming one splits its history.
- **Assets**: Import assets from `src/assets/` so Vite fingerprints them; nothing new goes in `public/`. Fonts come from Google Fonts via `<link>` in `index.html`.
- **Loading screen**: Every visit (desktop only) opens on `loading_screen.vue`, which downloads every file under `src/assets/audio/` and `src/assets/images/` (`asset_preloader.ts` finds them at build time), then waits for Start. Images are read back from the browser cache. Audio is handed to the game's players as an in-memory copy, because Firebase varies responses by encoding and a media request would miss the cache and download the file again; the players (created through `createAudioPlayer`) download nothing on their own until they first play. Pressing Start plays the menu click, then the requested address opens, and the press lets the music play. In development (`npm run dev`) the bar takes at least 0.5 s, so the loading state can be seen. Delete asset files that are no longer used, since they are downloaded too. The preloader's font list must match the faces requested in `index.html`. A file that fails is skipped and loads on demand later.
- **Recorded solutions**: `src/chambers/chamber_N.solution.json` is a run of chamber N recorded press by press (`ReplayData` in `src/game/replay_data.ts`; each press is an action, such as `"up"`, `"turnLeft"` or `"blue"`, or `"undo"` or `"redo"`), with what replaying it must give and the hash of the chamber it was recorded on (taken from the chamber as read). Record one by completing the chamber in `npm run dev` and pressing Download solution in the completion dialog (development builds only; it refuses when the run doesn't replay the same way), which names the file by the chamber's permanent id (it matches the file's number), then move it next to the chamber. Record it again whenever its chamber file changes (the replay check reports a changed chamber) or a rule change alters its route. Behaviour fixtures live in `scripts/fixtures/`, outside the catalogue: `fixtures.ts` pins, on tiny chambers of its own, how the rules play each change from the original rules, and how undo and redo replay. Solver fixtures live in `scripts/solver_fixtures/`: tiny chambers that pass the layout checks, each with a fewest-moves and a fewest-portals route counted by hand (never by a search, since they are the reference the solver is checked against) and a short argument for why each count is optimal.
- **No test suite**: This project has no tests by design. TypeScript, the type-aware lint rules and the engine checks (the recorded solutions, behaviour fixtures and solver fixtures replayed by `npm run replay:check`, the solver check, and the random walk) are the safety net — do not weaken `strict` or `noUncheckedIndexedAccess`, and do not add `any` to silence an error.
- **TypeScript projects**: `tsconfig.json` only references `tsconfig.app.json` (browser, `src/`, extends `@vue/tsconfig/tsconfig.dom.json`), `tsconfig.node.json` (`vite.config.ts`, extends `@tsconfig/node24`) and `tsconfig.scripts.json` (Node without the DOM, extends `@tsconfig/node24`: `scripts/`, the rules in `src/game/rules/`, the solver in `src/solver/`, the shared files they import, the chamber JSON and the fixture and solver fixture chambers; a file the scripts reach must be in its `include`, or the build fails; scripts import each other through its own `@scripts/` alias). An option the bases don't already cover must be set in all three.
- **Deploy**: `npm run deploy` builds into `dist/` (git-ignored) and runs `firebase deploy --only hosting` (project `portal-2d`). `firebase.json` rewrites every path to `/index.html` for history-mode routing.
- **Doc maintenance**: After changes, check whether `AGENTS.md`, `docs/elements.md` and `docs/solver.md` need updating.

## TypeScript

- No semicolons. Single quotes. One class per file. Named exports.
- Files `snake_case`; classes, interfaces and type aliases `PascalCase`; functions and variables `camelCase`.
- Full descriptive names — no `el`, `p`, `btn`. Allowed short names: `i`, `j` (loop counters), `x`, `y` (coordinates), `dx`, `dy` (deltas), `ctx` (canvas context).
- Always import with the `@` alias (mapped to `src/`; scripts reach other scripts with `@scripts/`). No relative paths, no file extensions. `import type` for type-only imports.
- No object shorthand: write `{level: level}`, not `{level}` (enforced). Objects and arrays with two or more items go one per line (enforced).
- No TypeScript `enum`: use string-literal unions, with a const object when named values help.
- Indexing a `Record` or array yields `T | undefined`: handle the miss rather than asserting it away with `!`.
- Prefer getters over methods for parameterless functions that only read state.
- Unused parameters: `_`, `__`, `___`.
- Comments: a JSDoc block on every class and function (no types — TypeScript declares them), an end-of-line comment on each field's first declaration, plain comments above non-obvious logic.
