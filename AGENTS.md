## Project

Portal 2D — a desktop-only, keyboard-driven puzzle game: the player crosses grid-based test chambers using a pair of portals (Vite + Vue 3, TypeScript, Composition API with `<script setup>`, vue-router, ESLint + @stylistic + type-aware typescript-eslint via @vue/eslint-config-typescript). It is a static site on Firebase Hosting; there is no backend.

`todo/` holds the author's roadmap: an overview (`README.md`) and one file per stage (`01_engine_v2.md` to `05_creator_platform.md`; stage 00 is done and its file removed). They are not planned work; do not build any of it unless asked, and only tick a stage's checkboxes for steps you were asked to do and finished.

## Layout

```
src/
  main.ts, app.vue, router.ts     entry, desktop-only and loading gates, routes (/, /chamber/:number)
  assets/styles.css               design tokens and shared classes (.wall, .room, .menu-row, .button-*, .keycap, .ruled-label)
  assets/audio/                   music and sound effects, imported so Vite fingerprints them
  assets/images/                  the test-room photo behind the home screen (WebP), the test-subject figure on chamber rows, the Aperture Science logo on the loading screen (SVG, small enough that Vite inlines it)
  chambers/chamber_N.json         chamber layouts (format: docs/elements.md); chamber_N.solution.json next to each is its recorded solution, read only by the engine scripts
  components/screens/             loading_screen (first screen of every visit), home_screen (the menu, in up to three columns), chamber_screen
  components/                     the home menu's chamber row, settings switch (both menu rows), chamber map (its third column, shown for Play), link row (a page in About's third column, opened in a new tab) and changelog list, legend, dialogs (dialog_frame is the shared shell), logo, desktop-only notice
  game/                           the game itself, plain TypeScript: the browser side (level, renderer, input, sounds, music, chamber preview) and what it shares with the rules (chamber data, directions, game keys, game events, a frame's input, the replay format, the text hash)
  game/classic/                   the rules, as translated from the original JavaScript: they play no sounds and use no browser API, so they also run under Node. Beside them, plain additions: the state snapshot and its hash, the settle step (one frame with keys, then empty frames until the state stops changing) and the replay runner
  services/                       chamber catalogue, changelog (releases shown under About), settings (sound/music), progress (completed chambers, best times and attempts, by chamber id), time format ("00:42.18"), last chamber (opened this visit, in memory), device detection, asset preloader, analytics (Firebase Analytics events)
docs/elements.md                  what each chamber element does
public/                           favicon only
scripts/                          the deploy script, and engine scripts run under Node with tsx: chamber_files (the chamber list they share), smoke_engine (every chamber loads and runs), check_replays (every recorded solution and behaviour fixture replays as expected), random_walk (seeded random inputs always settle; reports steps per second), fixtures/ (tiny chambers with replays pinning today's odd rule behaviour)
todo/                             the author's roadmap (not planned work, see above)
```

## Rules

- **After completing code changes**: Run `npm run lint:fix` and fix remaining errors, run `npm run build` (type-checks first) and fix any failures, then run `/delta-review` before responding. `npm run verify` runs the same lint (without fixing), the build and the engine checks, and changes no tracked file: `npm run smoke:engine` (every chamber file loads with the rules under Node and runs 100 empty frames), `npm run replay:check` (every chamber's recorded solution completes with its expected moves, portals and final hash, and every behaviour fixture ends as pinned) and `npm run random:walk` (100,000 seeded random steps per chamber, each settling within the cap; `--seed=` and `--steps=` change them); it is the whole-project check that later stages extend (`npm run check` is the fix-then-build shortcut).
- **Testing in the browser**: After code changes that can be seen or played, also test them yourself with the Chrome tool when it is connected: run `npm run dev` in the background, open a new tab and exercise the change (keys, clicks, screenshots, console). Keep the tab silent, because the user may be listening to something in another tab. The Chrome tools cannot mute a tab, so after every page load, before pressing Start, run `const play = HTMLMediaElement.prototype.play; HTMLMediaElement.prototype.play = function () { this.muted = true; return play.call(this) }` in the page: every sound effect and the music play through audio elements, and nothing plays before Start. Close the tab and stop the dev server when done, and say in the report what was tested this way and what was not.
- **Game/Vue boundary**: `src/game/` is plain TypeScript and never imports Vue, vue-router, `src/components/`, `src/services/` or `src/chambers/` (enforced in `eslint.config.js`). Screens drive it, not the other way around: `chamber_screen.vue` creates a `Level` on its canvas, sized in device pixels with the device pixel ratio (given on creation and to `resize`, refitted when the stage or the ratio changes; the renderer multiplies its fixed edge widths by the ratio, so ratio 1 draws exactly as before), calls `load` (also used for reset), `resize`, `dispose`, toggles `paused`, reads `started` and `elapsedHundredths` (the chamber clock) and `moves` and `portalsPlaced` (for analytics), gets `onCompleted` back, and in development calls `createReplay` for the completion dialog's Download solution. Each frame `Level` reads the keyboard once into a frame's input (the keys pressed, and whether the turn key is held), feeds the rules only that, and logs every frame with keys (with the count of empty frames before it, capped where the state has settled) and the state's hash after it; `createReplay` replays the log on a fresh chamber and refuses when any hash, the moves or the portals differ from the live run. The rules (`src/game/classic/`) play no sounds: they report what happens as `GameEvent`s (portal opened, refused, box picked up, fizzled, crossed, door or exit opened or closed, button pressed or released, switch used), and after each frame `Level` plays the matching `Sound` for each, in order, and counts the portals placed from them. They read keys by `GameKey` name (`Input` maps the physical keys). A stricter lint block for `src/game/classic/` forbids importing `sound`, `music`, `audio_sources`, `renderer`, `input` and `level`, and using `window`, `document`, `Audio`, `requestAnimationFrame` and `performance`; `tsconfig.scripts.json` type-checks the rules without the DOM. The clock starts on the first arrow, A, D, Space or Ctrl press after a load, counts only unpaused frames and skips the time a tab spent hidden. Services may import from `src/game/` (settings flips `Sound.enabled` and switches between `menuMusic`, played on the home screen and resumed where it left off, and `gameMusic`, played in a chamber and started over whenever a chamber opens, is reset or is replayed; the asset preloader hands each audio player its downloaded file through `useAudioFile` in `audio_sources.ts`). `Sound.MENU_BUTTON` and `Sound.START` are interface sounds the game never plays: components play the first on the loading screen's Start button, on dialog buttons, on every move of the home menu's highlight (keys, Tab or pointer), on opening and closing a home menu section, on stepping into and back from About's third column (not on opening Feedback or a page, which leave the game), on settings switches (after the change, so turning sound effects off stays silent) and on opening the pause menu or the reset progress confirmation, and the second when a chamber is started from the home menu. They obey the sound effects setting like every other `Sound`. Game objects are never made reactive and per-frame data never passes through a `ref`: the screen writes the timer's text straight into its element each frame.
- **Game behaviour is frozen**: The game was translated line by line from the original JavaScript, keeping its rules, update order, sounds and drawing exactly. Do not change rules, drawing, colours or sizes unless explicitly asked. Its colours are hex literals inside `src/game/`; leave them until the chamber visuals are reworked.
- **Keyboard ownership**: The game's `Input` owns the arrows, A, D, Space and Ctrl, and calls `preventDefault` on arrows and Space only while playing. Screens own Escape. On the home screen, which has no game running, Up and Down move the highlight within the column that has the keyboard (wrapping around; in the first column they change nothing else), Right or Enter opens the highlighted section and steps into it, Left or Escape closes it again. Under About the third column follows the highlighted row (a list of pages, or the changelog); Right, Enter or a click steps into the pages or the changelog (where Up and Down scroll it), and Left or Escape steps back to the About row. Arrows with Alt, Ctrl or Meta are left to the browser. Each column is one Tab stop (its highlighted row, or the changelog), and a held (repeating) Enter is ignored so it can't carry over from the previous screen. The first arrival shows only the sections, with Play highlighted and focused but not open; back from a chamber, Play is open with that chamber highlighted and focused. Hovering a row highlights it, in any column; clicking a section opens it like Enter. While any dialog is open the game is paused and its input is ignored (on the home screen, the menu ignores every key but Escape, which closes the dialog), and the dialog's buttons get the keyboard (`dialog_frame.vue`: first action focused, arrow keys and Tab move between actions). The loading screen's Start button takes focus once loading finishes.
- **Desktop only**: Touch-first devices (`pointer: coarse`) get the desktop-only notice instead of the app. Do not add mobile layouts or touch controls.
- **Chambers**: A chamber is a JSON file in `src/chambers/`, listed in `scripts/chamber_files.ts` (the engine scripts fail on a chamber file it doesn't list), with a recorded solution next to it, plus an entry in `src/services/chamber_catalogue.ts`: a permanent `id` (given in the order chambers were created, never reused or changed, so analytics history and stored progress survive reordering) and its layout. Its number is its position in the list, derived, never typed by hand; links (`/chamber/N`), the in-memory last chamber and the `chamber_number` analytics parameter follow it. In development, an id that is not a positive integer or is used twice is logged as an error. `ChamberData` (`src/game/chamber_data.ts`) must accept the JSON import without a cast, so the type checker validates every chamber file.
- **Persistence**: `localStorage` keys are prefixed `portal-2d.` and every access is wrapped in `try`/`catch` (storage can be blocked). Stored: sound on/off, music on/off, and the progress under one versioned key, `portal-2d.progress` (`{version: 2, chambers: {<id>: {completed, bestTime, attempts}}}`, by permanent chamber id; best times in hundredths of a second, attempts counted on each opening, Reset chamber and Play again). Reset progress under Settings stores an empty record. Version 1 kept completions and best times by chamber number (position) under `portal-2d.completed-chambers` and `portal-2d.best-times`; the first load that finds those keys merges them into the record (union of completions, the faster time) through a frozen number-to-id table in `progress.ts`, never the live catalogue, so a player returning after a reorder still maps correctly, then removes them. Malformed values are ignored; a record with a later version is left untouched (progress then lasts for the visit), so a rollback never erases it. Every save writes the whole record, so each tab takes over the record whenever another tab saves it (the `storage` event). The last chamber opened (which the home menu highlights on the way back) is kept in memory only.
- **Analytics**: `src/services/analytics.ts` sends Firebase Analytics events from production builds only (`npm run dev` sends nothing), with no consent prompt. Its config holds only `apiKey`, `projectId` and `appId`; the SDK fetches the measurement ID itself. Any failure (unsupported browser, ad blocker) silently drops events and never affects the game. Events: `chamber_start` (opened, or Play again), `chamber_restart` (Reset chamber confirmed), `chamber_quit` (Exit chamber or browser Back confirmed; not Back to menu or Next chamber after finishing, nor closing the tab), `chamber_abandon` (the page closed, reloaded or left for another site before finishing; at most once per attempt, and a lower bound, since events sent as a page goes away can be lost; a page restored from the back/forward cache carries on, so an attempt can be abandoned and later still end another way) and `chamber_complete`, each with `chamber_id`, `chamber_number` and `attempt` (the chamber's attempt count on this device, cleared by Reset progress; a restart ends attempt N and the next run is N + 1), all but `chamber_start` also with `time_ms` (the time shown) and `moves` (tiles stepped onto), and `chamber_complete` also with `portals` (portals placed, misses not counted), `first_completion` and `new_best` (1 or 0; after Reset progress the next completion counts as first again). Reset chamber sends no `chamber_start` of its own, so runs = `chamber_start` + `chamber_restart`; `setting_change` (`setting`: sound or music, `enabled`: on or off), `progress_reset`, `changelog_open` (stepping into the changelog, not just highlighting its row), `feedback_open` and `link_open` (`link`, `url`). Event and parameter names are permanent: renaming one splits its history.
- **Assets**: Import assets from `src/assets/` so Vite fingerprints them; nothing new goes in `public/`. Fonts come from Google Fonts via `<link>` in `index.html`.
- **Loading screen**: Every visit (desktop only) opens on `loading_screen.vue`, which downloads every file under `src/assets/audio/` and `src/assets/images/` (`asset_preloader.ts` finds them at build time), then waits for Start. Images are read back from the browser cache. Audio is handed to the game's players as an in-memory copy, because Firebase varies responses by encoding and a media request would miss the cache and download the file again; the players (created through `createAudioPlayer`) download nothing on their own until they first play. Pressing Start plays the menu click, then the requested address opens, and the press lets the music play. In development (`npm run dev`) the bar takes at least 0.5 s, so the loading state can be seen. Delete asset files that are no longer used, since they are downloaded too. The preloader's font list must match the faces requested in `index.html`. A file that fails is skipped and loads on demand later.
- **Recorded solutions**: `src/chambers/chamber_N.solution.json` is a run of chamber N recorded frame by frame on today's rules (format: `ReplayData` in `src/game/replay_data.ts`, plus the chamber's permanent `chamberId`), with what replaying it must give and the hash of the chamber it was recorded on. Record one by completing the chamber in `npm run dev` and pressing Download solution in the completion dialog (development builds only), which names the file by the chamber's permanent id (it matches the file's number), then move it next to the chamber. Record it again whenever its chamber file changes (the replay check reports a changed chamber) or a rule change alters its route. Behaviour fixtures live in `scripts/fixtures/` (listed in `fixtures.ts`), outside the catalogue.
- **No test suite**: This project has no tests by design. TypeScript, the type-aware lint rules and the engine checks (the recorded solutions and behaviour fixtures replayed by `npm run replay:check`, and the random walk) are the safety net — do not weaken `strict` or `noUncheckedIndexedAccess`, and do not add `any` to silence an error.
- **TypeScript projects**: `tsconfig.json` only references `tsconfig.app.json` (browser, `src/`, extends `@vue/tsconfig/tsconfig.dom.json`), `tsconfig.node.json` (`vite.config.ts`, extends `@tsconfig/node24`) and `tsconfig.scripts.json` (Node without the DOM, extends `@tsconfig/node24`: `scripts/`, the rules in `src/game/classic/`, the shared files they import, the chamber JSON and the fixture chambers; a file the scripts reach must be in its `include`, or the build fails; scripts import each other through its own `@scripts/` alias). An option the bases don't already cover must be set in all three.
- **Deploy**: `npm run deploy` builds into `dist/` (git-ignored) and runs `firebase deploy --only hosting` (project `portal-2d`). `firebase.json` rewrites every path to `/index.html` for history-mode routing.
- **Doc maintenance**: After changes, check whether `AGENTS.md` and `docs/elements.md` need updating.

## TypeScript

- No semicolons. Single quotes. One class per file. Named exports.
- Files `snake_case`; classes, interfaces and type aliases `PascalCase`; functions and variables `camelCase`.
- Full descriptive names — no `el`, `p`, `btn`. Allowed short names: `i`, `j` (loop counters), `x`, `y` (coordinates), `dx`, `dy` (deltas), `ctx` (canvas context).
- Always import with the `@` alias (mapped to `src/`; scripts reach other scripts with `@scripts/`). No relative paths, no file extensions. `import type` for type-only imports.
- No object shorthand: write `{level: level}`, not `{level}` (enforced). Objects and arrays with two or more items go one per line (enforced).
- No TypeScript `enum`: use string-literal unions, with a const object when named values help.
- Indexing a `Record` or array yields `T | undefined`: handle the miss rather than asserting it away with `!`.
- Prefer getters over methods for parameterless functions that only read state.
- Unused parameters: `_`, `__`, `___`.
- Comments: a JSDoc block on every class and function (no types — TypeScript declares them), an end-of-line comment on each field's first declaration, plain comments above non-obvious logic.

## UI

- Always use the `frontend-design` skill when changing the UI.
- Direction: test-facility signage. Cool light panels on a seamed wall (the home screen sits on a photo of a test room instead, via `.room` and `.room-inner`, which keep its content on the room's back wall, clear of the side walls and floor, with the wordmark above the menu; the chamber screen puts the game on the same photo, blurred so the eye stays on the chamber, beside a light rail holding the wordmark, the chamber sign (a spaced label and rule, ending in the timer with a stopwatch, over the two-digit number) and the controls legend (keycaps, then a divider, blue or orange for the portal keys, before what each key does); the loading screen sits on the seamed wall with larger panels, rivets where the seams cross and a soft vignette, under the Aperture Science logo, muted), the home menu as lettering straight on the room's wall, with no panel (Play, Settings and About; once a section is opened, its rows in sign capitals beside them, the first level with the section's own row (a cascade, from the shared `--menu-row-height`), for Play the highlighted chamber's map, and for About, level with the highlighted row, the pages as rows ending with an arrow leaving a box (they open a new tab), or the changelog beside a thin rule that darkens when it has the keyboard; the row with the keyboard sits on a see-through dark bar with white lettering, which is also its focus mark, and the chosen row of a column without the keyboard on a fainter one; a chamber row ends with the best time, when there is one, and the test-subject figure, grey until the chamber is completed and green after; Settings ends with Reset progress, a plain row that leaves the red to its confirmation dialog), thin rules, chamber numbers as large sign numerals, and the game's own colours as the only accents: blue marks interaction and success (the pause dialog's band and Continue button, the chamber-complete dialog's band and main button: Next chamber, or Back to menu after the last chamber), orange is the second portal (the wordmark and the legend), the floor button's red marks caution (actions that discard progress: the confirmation dialog's band and button), and the test subject's green marks a completed chamber on its row. Keep these meanings consistent.
- Tokens live on `:root` in `src/assets/styles.css` (`--color-wall`, `--color-panel`, `--color-rule`, `--color-white`, `--color-ink`, `--color-ink-muted`, `--color-blue`, `--color-blue-deep`, `--color-orange`, `--color-red`, `--color-red-deep`, `--color-subject`, `--color-chamber`, plus `-rgb` triplets for alpha). Use tokens, not new colours.
- Type: `Barlow Condensed` for display (wordmark, sign numerals, titles), `Barlow` for everything else.
- CSS colours are always `rgba()`, never hex (the game's canvas colours are the exception, see above). `border-radius` in `rem` (exception: `50%` for circles).
- Repeated CSS goes to `src/assets/styles.css`; component-specific styles stay in scoped `<style>` blocks.
- Accessibility floor: visible keyboard focus, keyboard-operable dialogs and switches, and `prefers-reduced-motion` respected (global rule in `styles.css`).
- Copy is sentence case, plain verbs; a button says what it does ("Reset chamber", not "OK"). Signage labels may be shown in capitals with `text-transform`; the text itself stays sentence case.
- CSS comments: `/* ==== */` block dividers for major sections, a short phrase above a rule for its purpose.
