## Project

Portal 2D — a desktop-only, keyboard-driven puzzle game: the player crosses grid-based test chambers using a pair of portals (Vite + Vue 3, TypeScript, Composition API with `<script setup>`, vue-router, ESLint + @stylistic + type-aware typescript-eslint via @vue/eslint-config-typescript). It is a static site on Firebase Hosting; there is no backend.

`todo/` holds the author's roadmap: an overview (`README.md`) and one file per stage (`04b_campaign.md` and `05_creator_platform.md`; stages 00, 01, 03 and 04a are done, stage 02 stopped after its prototype, and their files are removed; what stage 02 learned is in `docs/solver.md`; the 04a decisions 04b cites are copied into it), and `future.md`, ideas for mechanics beyond the plan and how a mechanic was built. They are not planned work; do not build any of it unless asked, and only tick a stage's checkboxes for steps you were asked to do and finished.

## Rules

- **After completing code changes**: Run `npm run lint:fix` and fix remaining errors, run `npm run build` (type-checks first) and fix any failures, then run `/delta-review` before responding. `npm run verify` runs the same lint (without fixing), the build, the bundle and asset checks and the engine checks, and changes no tracked file: `npm run bundle:check` (the files in `dist/assets`, totalled by kind: JS, CSS, images, audio and any other, each fails when it grows by more than both 10% and 10 KB over `scripts/bundle_baseline.json`; after a growth you accept, `npm run bundle:baseline` builds and records a new baseline), `npm run assets:check` (since the loading screen downloads every file under `src/assets/`, each must be imported, or named in a CSS `url()`, by a source the build ships (`src/` but `src/dev/`, and `index.html`), a mention in a comment not counting; the sprites' folder, read by name instead, holds exactly one `.webp` or `.png` per sprite, of a size its shape allows (read from the file's header), and no folder), `npm run smoke:engine` (every chamber file and the playground loads with the rules under Node and settles its start, printing its state's size and hash), `npm run replay:check` (every chamber's recorded solution completes with its expected moves, portals and final hash, and then no action changes the completed chamber or reports anything; every behaviour fixture in `scripts/fixtures/fixtures.ts` ends as pinned; both routes of every solver fixture in `scripts/solver_fixtures/solver_fixtures.ts`, on its chamber loaded with the layout checks, complete with their pinned counts and final hash), `npm run solver:check` (every state along each chamber's recorded solution and 100,000 seeded random steps packs into the solver's state key and unpacks unchanged; a chamber too large for the key is refused; from every state along the recorded solutions and every state the reference search finds on the solver fixtures, each walk the walk graph allows gives through the rules' step the state the solver builds, no move it leaves out lands on a plain neighbouring tile, each turn gives the state built for that facing, each shot from each tile a walk reaches, each way and colour, gives the state the solver builds from the shot it shares with its line, each move the solver skips as changing nothing changes nothing through the rules' step but where the subject faces, and so does each interact it skips, each way the subject may face, unless it gives what an interact the solver takes there gives (not the box drops the any-route search leaves out, a guess this doesn't check), and a tile a walk reaches is in the start's region exactly when a walk from it gets back to the start, all but the key's round trip skipped on a chamber with a receiver, which the macro search refuses, its line saying why; on every solver fixture the reference search and the macro search find both hand-counted pars, the macro search also finds a route in its solvable mode, every route replays to the same counts, and every state the reference search found survives the key with a key of its own), `npm run random:walk` (100,000 seeded random actions per chamber, on the playground and per fixture chamber, the fixture chambers read without the layout checks, each settling within the rules' pass cap, with the speed and the state's size; - **Testing in the browser**: After code changes that can be seen or played, also test them yourself with the Chrome tool when it is connected: run `npm run dev` in the background, open a new tab and exercise the change (keys, clicks, screenshots, console). Keep the tab silent, because the user may be listening to something in another tab. The Chrome tools cannot mute a tab, so after every page load, before pressing Start, run `const play = HTMLMediaElement.prototype.play; HTMLMediaElement.prototype.play = function () { this.muted = true; return play.call(this) }` in the page: every sound effect and the music play through audio elements, and nothing plays before Start. - **Game/Vue boundary**: `src/game/` is plain TypeScript and never imports Vue, vue-router, `src/components/`, `src/services/` or `src/chambers/` (enforced in `eslint.config.js`). Screens drive it, not the other way around: `chamber_screen.vue` creates a `Level` on its canvas with the player's key bindings (a plain object, read once), sized in device pixels (refitted when the stage or the device pixel ratio changes; the drawing scales with the tile size alone; the tiles are sized as if the chamber were at least 16 tiles each way, so a smaller one is drawn no larger than that and sits centred in the stage, while the home menu's map always fills its box), calls `load` (also used for reset), `resize`, `dispose`, toggles `paused`, reads `started` and `elapsedHundredths` (the chamber clock) and `moves` and `portalsPlaced` (for analytics), gets `onCompleted` back, and in development calls `createReplay` for the completion dialog's Download solution and sets `frameStats` (`src/game/frame_stats.ts`), which the level tells of each frame, drawing and rules step, timing them only while it is set, and whose samples the screen hands to the performance view. `Input` queues presses in arrival order (a held key's repeat is dropped while its earlier press still waits), each with whether the turn key was held as it went down; the turn key itself is never queued, only read as held. Each frame `Level` takes the oldest press as one action of the rules' step (`step` in `src/game/rules/step.ts`), which carries out every consequence of the action before it returns, so live play takes one action per frame, in the order pressed; while paused nothing is queued, and resuming forgets every press still waiting and every key held; the window losing focus forgets every key held, since their keyup goes elsewhere. A move key pressed while the turn key is held (Shift by default) is a turn action: the subject faces that way without moving, unless it already faces that way, when it moves, as the rules say; it starts the clock and is logged like any press. `Level` redraws when the state changes, and while a step is being drawn (`StepAnimation`, `src/game/step_animation.ts`: about 120 ms from the state before it to the state after it, eased out and started one frame back, so the press's own frame already shows part of it; a slide along its path at one tile every 60 ms, a portal crossing counting as two, its last tile eased out, so a six-tile slide takes about 0.42 s; a step that completes the chamber with the subject arriving on the exit the way out of its outer wall walks it out: no easing, a move at 180 ms a tile, a slide at its own pace, across the exit and on until it is a whole tile past the chamber's edge, then held there) every frame, paused or not, until a frame draws its end, which the renderer then draws exactly as the plain state; it also draws every frame, paused or not, while anything glows (a laser that is on or an open portal whose glow has a file), pieces break up, a box falls, a missed shot ripples, a portal opens, the subject turns, or an arrow, a blocked wall, a ditch, a door, the exit, a fizzler, a laser, a light barrier or a receiver's eye changes, and once more when that stops (a ray's glow, held steady, isn't among them); otherwise idle frames draw nothing. A step that reports `fizzled`, or `portalFizzled` (a fizzler switching on closed a portal facing it), breaks up what it took (`FizzleParticles`, `src/game/fizzle_particles.ts`: each portal open before it and closed after it, and a box carried before it and gone after it, where it was carried; with `portalFizzled` alone, only a portal whose wall side faced a fizzler that is on after it, so one a blocked wall closed in the same step still just vanishes), replacing pieces still drifting unless it took nothing, or it is a later part of the same slide, whose pieces join them. A step that reports `boxDestroyed` breaks up each box a door closing or a laser, a light barrier or a fizzler switching on destroyed where it lay, the same way, and drops each box a ditch destroyed into the pit (`BoxFall`, `src/game/box_fall.ts`), replacing a fall still running unless it dropped nothing; both find those boxes with `findDestroyedBoxes` (`src/game/destroyed_boxes.ts`). A portal shot the rules refuse ripples where `shotStop` says it stopped (`MissRipple`, `src/game/miss_ripple.ts`), replacing a ripple still spreading; a refused crossing or interact shows none, and a shot from inside a fizzler that is on reports nothing and shows none. A step that reports `bluePortalOpened` or `orangePortalOpened` grows that portal open on its wall (`PortalOpenings`, `src/game/portal_openings.ts`), replacing an opening of that portal still running; a portal that moves or closes while it opens is drawn as it is, the one a shot moved away still vanishes at once, and one that breaks up while it opens breaks up whole. Any step that turns an arrow rotates its chevron, any step that switches a blocked wall slides its steel apart or shut, any step that switches a ditch slides its grate in or out, any step that opens or closes a door or the exit slides it, any step that switches a fizzler off or on crumbles its field away or forms it, any step that switches a laser or a light barrier fades it, and any step that lights or darkens a receiver fades its eye (`ElementTransitions`, `src/game/element_transitions.ts`, comparing each receiver's lit flag as it compares blocked flags), from where it is drawn if it was still changing; a ray and an emitter's lens change at once with the step. No press waits for them or cuts them short, and a load clears them. With `prefers-reduced-motion` the glows hold steady, nothing breaks up, falls, opens, slides, turns, crumbles, fades or ripples and only changes are drawn. Part way through a step, the subject and a box it carries through it are drawn at the subject's pose (`src/game/subject_pose.ts`): a move glides one tile, a portal crossing slides into the entry portal, facing it, then out of the exit one, each half clipped to its tile, and a slide goes the same ways leg by leg along its path, a walk-out carries it on past the exit, unclipped, until the chamber's edge cuts it off, the distance still to go rounded to whole canvas pixels, the subject drawn as one of its two sprites (on a layer of its own while the chamber is completed, the exit's shadow laid over its pixels only, so it darkens on the exit) (`subject_holding_box` while it carries a box, a mirror box's mirror marked over it, else `subject_holding_gun`); everything else shows the state after the step at once, but the subject turns (`SubjectTurn`, `src/game/subject_turn.ts`) whenever the way it is drawn facing changes: a turn in place, a move another way, a walk into a wall, into a portal and along a slide, from the angle drawn, the shorter way round (a half turn clockwise), over about 0.1 s a quarter turn and 0.15 s a half, eased out and started one frame back; a press never cuts a turn short (the next turn carries on from the angle drawn), and coming out of a portal, or a press ending a crossing before it came out, it faces its new way at once; a load clears it. A load or a resize redraws at the latest frame's time, so a step being drawn never goes back. Only a rules step that changes the state starts one; every press taken ends the running one at once (a new key never waits), even a press that changes nothing; a load and a reset show their state at once; with `prefers-reduced-motion` (read by `Level` each time a step would start one) nothing is drawn over time. Sounds, the counters, the log and `onCompleted` stay in the frame that takes the press, and the clock is unaffected, but for a step that slid, drawn over time: the counters and the log stay at the press, while what happened on each tile it entered (its sounds, a fizzle's break-up) waits until the subject is half way into that tile, or through the portal onto it, and its stop and settling (buttons, doors, the element transitions, `onCompleted`) until the slide ends; until then everything but the subject is drawn as the state on the last tile it has reached. A press first plays all that a slide still has waiting; a load or a reset drops it. The clock stops at the press that completes the chamber, though `onCompleted`, which pauses the game, may wait for a slide and waits for a walk-out to end, everything else staying at the press but what a slide's stop sets off. A load settles the chamber's start and plays the sounds of its events. `Level` reads the completion from the state after each step and then calls `onCompleted`; once the chamber is completed nothing runs, and every press, held repeats included, is dropped without cutting a walk-out or a slide onto the exit short. `moves` counts each step that puts the subject on another tile, a portal crossing included. `Level` logs every action it takes and the state's hash after it, and `createReplay` replays the log with the replay runner and refuses when any hash, the moves or the portals differ from the live run. The rules (`src/game/rules/`) play no sounds: they report what happens as `GameEvent`s (portal opened, refused, box picked up, box put down, a box destroyed where something blocks, fizzled, a portal closed by a fizzler switching on, crossed, door or exit opened or closed, button pressed or released, switch used, a slide started or stopped, an arrow turned, a blocked wall or a ditch switched, a receiver lit or gone dark), and after each step `Level` plays the matching `Sound` for each (a portal closed by a fizzler switching on, a destroyed box, a slide's start and stop and a receiver lighting or going dark have none), in order, and counts the portals placed from them; a portal shot that misses plays `Sound.SHOOT` instead of the error sound (a hit plays only its portal's sound, and a shot from inside a fizzler that is on fires nothing and stays silent). They take actions (four moves, four turns, two shots, interact), which `Level` makes from the presses (`Input` maps the physical keys to `GameKey`s); a move key turns instead of moving while the turn key is held. A stricter lint block for `src/game/rules/` forbids importing `sound`, `music`, `audio_sources`, `renderer`, `input`, `level`, `tile_painter`, `element_drawings`, `step_animation`, `subject_pose`, `subject_turn`, `fizzle_particles`, `box_fall`, `destroyed_boxes`, `element_transitions`, `miss_ripple`, `portal_openings`, `ray_drawing`, `piece_number`, `sprite_set`, `sprite_sources`, `sprite_scaling`, `surface_noise`, `surface_tone`, `wear_marks` and `exit_shadow`, and using `window`, `document`, `Audio`, `requestAnimationFrame` and `performance`; `tsconfig.scripts.json` type-checks the rules without the DOM. The solver (`src/solver/`) has a block of its own with the same bans, plus `@scripts/*`, Node's modules (`node:*`) and `process`, so it can also run in a Web Worker; it may import `src/game/`, never Vue, components, services or chambers. The clock starts on the first press of a move, portal or interact key after a load, counts only unpaused frames and skips the time a tab spent hidden. Services may import from `src/game/` (settings flips `Sound.enabled` and switches between `menuMusic`, played on the home screen and resumed where it left off, and `gameMusic`, played in a chamber and started over whenever a chamber opens, is reset or is replayed; the asset preloader hands each audio player its downloaded file through `useAudioFile` in `audio_sources.ts`). `Sound.MENU_BUTTON` and `Sound.START` are interface sounds the game never plays: components play the first on the loading screen's Start button, on dialog buttons (pressed, or reached by the keyboard's arrows or Tab), on every move of the home menu's highlight (keys, Tab or pointer), on opening and closing a home menu section, on stepping into and back from About's or Controls' third column (not on opening Feedback or a page, which leave the game), on settings switches (after the change, so turning sound effects off stays silent), on picking a layout under Controls (with Custom, also opening its dialog), on a custom controls row starting to wait for a key and on a key bound, on opening the pause menu or the reset progress confirmation, and on Escape closing a dialog or stepping back from a confirmation to the pause menu (not on Escape cancelling a custom controls row's wait), and the second when a chamber is started from the home menu. They obey the sound effects setting like every other `Sound`. Game objects are never made reactive and per-frame data never passes through a `ref`: the screen writes the timer's text straight into its element each frame. The home menu's map (`chamber_preview.ts`) draws each chamber's settled start with the same renderer.
- **Rules are pinned, the look follows the sprite spec**: The rules are defined in `docs/elements.md` (each element, the step, and every change from the original game's rules) and pinned by the recorded solutions and the behaviour fixtures. Change a rule only when explicitly asked, and then in the same change re-record the solutions (and fixtures) it alters and update `docs/elements.md`. The chamber is drawn from the sprites `docs/sprites.md` describes, each drawn in code as an SVG in `art/sprites/` and exported to its file, but for the subject's painted sprites (`docs/sprites.md`): don't change how sprites are placed, their art or the palette unless asked, and change a sprite's art in its source, then export it again. There is no stand-in drawing: a sprite whose file is missing, refused or failed to download isn't drawn, so `npm run assets:check` requires every sprite's file, of a size its shape allows, and a new element's sprites need their files before they are added to the set. The palette (`src/game/palette.ts`) holds only the colours drawn by code, the background behind the floor, the shared shadow, a missed shot's ripple in each portal's colour, the antlines' dots and their borders, unlit and lit, an emitter's ray, from its dark rim to its white-hot core, the strokes marking a carried mirror box's mirror, the surface detail's tints and marks, each drawn faint, and the open exit's shadow at its darkest (the last five with no CSS token, as the menus don't use them); the background is mirrored by hand in `--color-chamber`, the ripple's colours in `--color-blue` and `--color-orange`, and the meaning colours (`docs/sprites.md`) by hand in the CSS tokens and the sprites, so change them together.
- **Keyboard ownership**: The game's `Input` owns the keys bound to its game keys (`src/game/key_bindings.ts`), keys read by physical position (`KeyboardEvent.code`) so they stay in place on every layout. The player picks a layout of controls under Settings: Default (the arrows, A and D (portals), Space (interact) and Shift, held to turn in place) or Custom (their own, set in its dialog, starting from Default the first time it is picked). On trial, Default (bindings holding exactly its keys) also turns with Ctrl held, as a second turn key the game shows nowhere (not in the legend, Settings or the custom controls dialog); either turn key can be let go while the other stays held. The mouse plays no part in the game. One key per game key, never shared; a left/right modifier pair counts as one key; Escape, Tab, Alt, Meta and the F-keys can't be bound. Held keys repeat with the key's auto-repeat. While playing, it calls `preventDefault`, on keydown and keyup, only for bound keys with a browser default (the arrows, Space, Page Up/Down, Home, End, Enter, Numpad Enter, the keys where a US keyboard has / and ', and any key that types Firefox's quick-find / or ' on the player's layout), and for every bound key with Ctrl held (Ctrl+A would select the page, Ctrl+D bookmark it), never with Alt or Meta held; a key pressed with Alt or Meta held is left to the browser and doesn't play (it only counts as held). Keys are shown with the label the player's layout prints (`navigator.keyboard.getLayoutMap()` in Chromium, a US keyboard elsewhere), and the arrow keys as small triangles pointing their way. The numpad's keys are keys of their own, so with NumLock off its arrows don't move the subject unless bound (the menus, which read `event.key`, still follow them). Screens own Escape: in a chamber, Escape (not a held repeat) opens the pause menu, closes it, steps back from the restart or exit confirmation to it, and does nothing on the completion dialog; browser Back opens the exit confirmation, and leaves once it is confirmed or the chamber is finished. On the home screen, which has no game running, Up and Down move the highlight within the column that has the keyboard (wrapping around; in the first column they change nothing else), Right or Enter opens the highlighted section and steps into it, Left, Escape or Backspace closes it again; until any chamber has been opened on this device (no chamber has an attempt in the progress, so again after Reset progress), Enter, Space or a click on Play starts the tutorial instead, with the start sound, and Right still opens the chamber list. Under About the third column follows the highlighted row (a list of pages, or the changelog); Right, Enter or a click steps into the pages or the changelog (where Up and Down scroll it), and Left, Escape or Backspace steps back to the About row. Under Settings, the Controls row's third column starts level with it: Default and Custom; Right, Enter or a click steps in (on the layout in use) and Left, Escape or Backspace steps back, as under About. Enter, Space or a click on a layout puts it in use; on Custom it also opens the custom controls dialog (`custom_controls_dialog.vue`): one row per game key, then Done, with labels re-read from the layout as it opens. Enter, Space or a click on a key's row waits for its next key: while it waits, every keydown is taken before the dialog and the screen see it (so Ctrl and Shift can be bound), a held key's repeats are ignored, the key is bound (a game key that held it takes the old one), Escape cancels silently, and a key that can't be bound shows "Can't use" and the key's name and keeps waiting; a click anywhere, the waiting row included, cancels, and the release of a taken key and the click on the waiting row are kept from pressing the row again. Binding edits Custom. Screen-reader status lines announce the layout put in use, and the dialog's wait, refusals and binds. On the home screen, the menu's keys with Alt, Ctrl or Meta are left to the browser, and Space presses any row but a link (a chamber, a page, Feedback), where it does nothing. Each column is one Tab stop (its highlighted row, or the changelog), and a held (repeating) Enter is ignored so it can't carry over from the previous screen. The first arrival shows only the sections, with Play highlighted and focused but not open; back from a chamber, Play is open with that chamber highlighted and focused. Opening Play highlights the first chamber not yet completed, or the first chamber when all are. In development the first column starts with Playground, which opens no section: Enter, Space or a click starts the playground with the start sound, Right does nothing; the first arrival highlights and focuses Playground instead of Play, and back from it only the sections show, with Playground highlighted and focused. Moving the pointer onto a row (not a row appearing under a still pointer) highlights it and gives its column the keyboard, in any column; clicking a section opens it like Enter. While any dialog is open the game is paused and its input is ignored (on the home screen, the menu ignores every key but Escape, which closes the dialog), and the dialog's buttons get the keyboard (`dialog_frame.vue`: first action focused, Up and Down (stacked actions) or Left and Right (actions in a row, the confirmation's) and Tab move between actions, the other two arrows doing nothing, and a held (repeating) Enter or Space presses nothing, so a move key bound to one can't carry into a dialog). The loading screen's Start button takes focus once loading finishes.

- **Chambers**: A chamber is a JSON file in `src/chambers/`, listed in `scripts/chamber_files.ts` (the engine scripts fail on a chamber file it doesn't list), with a recorded solution next to it, plus an entry in `src/services/chamber_catalogue.ts`: a permanent `id` (0 or more: 0 is the tutorial's, the others are given in the order chambers were created; it names the chamber's files, keys its stored progress and is sent as the analytics `chamber_id`, so changing one splits that chamber's analytics history), its layout and, optionally, a name the player sees instead of "Chamber N" in the home menu and the chamber-complete dialog (the tutorial's is "Tutorial"). Its number is its position in the list, counted from 0, derived, never typed by hand; links (`/chamber/N`), the in-memory last chamber and the `chamber_number` analytics parameter follow it. In development, an id that is not a whole number of 0 or more, or is used twice, is logged as an error. Chamber files are in format 2 (`"version": 2`, described in `docs/elements.md` under "Chamber format"): `ChamberData` (`src/game/chamber_data.ts`: a `version`, lists that may be left out, blocked walls (walls that refuse portals while blocked, a one-tile one linkable), link groups sharing the element ids, antlines (dotted lines on the floor from a button, switch or receiver to one element it links, by id, never a group, along corner tiles that share a row or a column; only drawn, lit while that element is unblocked, optional and meant mostly for the tutorial and the early chambers), an empty par block; its element fields are typed from the element registry in `src/game/rules/element_registry.ts`, each by its definition's entry type) must accept the JSON import without a cast, so the type checker validates every chamber file, and `scripts/fixtures/format_examples.ts` types a format 2 example the same way. Type checking can't catch a misspelled or unknown field in an imported file, so the chamber loader (`src/game/rules/load_chamber.ts`) does: it reads a file as raw JSON, refuses any `version` but 2, and rejects what `docs/elements.md` lists under "What the validator rejects". The level and the home menu's map load every chamber through it and throw on a chamber it rejects, so `npm run chamber:check`, which runs it on every chamber file, must pass. The playground (`src/dev/playground.json`, format 2, edited by hand) is a development-only chamber outside the list for trying every element: from the start, each direction tests one group, switched by the button one step that way (up the door and the exit, between blocked side walls; right two lasers crossing; down the fizzler, three light barriers side by side across the room (so its far row needs a box on the button) and a blocked wall in the bottom wall, taking portals while the button is held; left the ditches, and past them, down through a gap in the floor of the left arm, a slide room in the bottom left corner: slide floor throughout, with a fizzler field across it, held off by a button on the slide floor that the room's own box can hold down), and the middle room holds the four arrows, one of them, on the left, turned up by its own button below it while that is held, so stepping up off the button onto it turns it back under the subject, two boxes and a switch that sends them back; up from its top right corner, a ray room in the chamber's top right corner: an emitter in its right wall, off until the button in the room's top right corner is held, fires left along the room's bottom row, over a switch (so the ray is seen drawn over it) that sends the room's mirror box back, into a wall that takes portals, and the mirror box put in the ray's way, or a portal pair from that wall to the room's bottom wall, sends it up to a receiver in the top wall, which opens a door in the room's top left corner, clear of the ray; The home menu's Playground row (development builds only) opens it at `/playground` in the chamber screen, which keeps no progress for it, sends no analytics, isn't the last chamber, shows "--" on its sign for the number and its place in the list (a screen reader hears "Playground"), and offers no Next chamber, best time or Download solution; production builds leave out the row, the address and the file. - **Persistence**: `localStorage` keys are prefixed `portal-2d.` and every access is wrapped in `try`/`catch` (storage can be blocked). Stored: sound on/off and music on/off (`true` or `false`, on unless `false`, read once per visit, so not synced between tabs), the controls under `portal-2d.key-bindings` (`{layout, custom}`: the layout in use, `arrow-keys` (shown as Default) or `custom`, and the Custom keys, a plain object, game key → key (its `KeyboardEvent.code`, `Control` or `Shift` for either side), or null until Custom is first picked; Default's keys are never stored, so a change to them always takes effect; Custom keys are read game key by game key, a stored key that can't be bound (the mouse buttons once bound, `MouseLeft` and `MouseRight`, included) or is already taken falls back to that game key's Default key, and if that is then taken every game key goes back to Default; a layout that isn't one (the retired `wasd-mouse` included), or Custom with no keys, falls back to Default; renaming a game key or a key name sends a stored binding of it back to Default; unlike the progress, it is not synced between tabs, so a tab keeps the controls it loaded until it reloads), and the progress under one versioned key, `portal-2d.progress` (`{version: 2, chambers: {<id>: {completed, bestTime, attempts}}}`, by permanent chamber id; best times in hundredths of a second, attempts counted on each opening, Restart chamber and Play again). Reset progress under Settings stores an empty record. Malformed values, unknown fields and a record of another version are ignored. Stored formats may change without a migration: a stored value that no longer reads is ignored and falls back to its default (decision 13 in `todo/README.md`: friends' saves may be reset by updates). Every save writes the whole record, so each tab takes over the record whenever another tab saves it (the `storage` event). The last chamber opened (which the home menu highlights on the way back), or the playground in development, is kept in memory only.
- **Analytics**: `src/services/analytics.ts` sends Firebase Analytics events from production builds only (`npm run dev` sends nothing, but `npm run preview` serves a production build and sends real events), with no consent prompt. Its config holds only `apiKey`, `projectId` and `appId`; the SDK fetches the measurement ID itself. Any failure (unsupported browser, ad blocker) silently drops events and never affects the game. Events: `chamber_start` (opened, or Play again), `chamber_restart` (Restart chamber confirmed), `chamber_quit` (Exit chamber or browser Back confirmed; not Back to menu or Next chamber after finishing, nor closing the tab), `chamber_abandon` (the page closed, reloaded or left for another site before finishing; at most once per attempt, and a lower bound, since events sent as a page goes away can be lost; a page restored from the back/forward cache carries on, so an attempt can be abandoned and later still end another way) and `chamber_complete`, each with `chamber_id`, `chamber_number` and `attempt` (the chamber's attempt count on this device, cleared by Reset progress; a restart ends attempt N and the next run is N + 1), all but `chamber_start` also with `time_ms` (the time shown) and `moves` (steps that put the subject on another tile), and `chamber_complete` also with `portals` (portals placed, misses not counted), `first_completion` and `new_best` (1 or 0; after Reset progress the next completion counts as first again). Restart chamber sends no `chamber_start` of its own, so runs = `chamber_start` + `chamber_restart`; `setting_change` (`setting`: sound or music, `enabled`: on or off; changing the controls sends nothing), `progress_reset`, `changelog_open` (stepping into the changelog, not just highlighting its row), `feedback_open` and `link_open` (`link`: the page's name on its row, `url`). Event and parameter names are permanent: renaming one splits its history.
- **Assets**: Import assets from `src/assets/` so Vite fingerprints them; nothing new goes in `public/`. Fonts come from Google Fonts via `<link>` in `index.html`.
- **Loading screen**: Every visit (desktop only) opens on `loading_screen.vue`, which downloads every file under `src/assets/audio/` and `src/assets/images/` (`asset_preloader.ts` finds them at build time), then waits for Start. Images are read back from the browser cache, except the chamber sprites (`src/assets/images/chamber/`), which are handed to the game decoded (`useSpriteFile` in `sprite_sources.ts`) before Start; in development, a file there that isn't a sprite's, or a sprite's file of the wrong size, is logged as an error. In development (`npm run dev`) the bar takes at least 0.5 s, so the loading state can be seen. A file that fails is skipped and loads on demand later; a chamber sprite that fails, can't be decoded or has the wrong size isn't drawn for the rest of the visit, and a dev page, which skips the loading screen, loads the sprites itself (`loadSprites`).
- **Recorded solutions**: `src/chambers/chamber_N.solution.json` is a run of chamber N recorded press by press (`ReplayData` in `src/game/replay_data.ts`; each press is an action, such as `"up"`, `"turnLeft"` or `"blue"`), with what replaying it must give and the hash of the chamber it was recorded on (taken from the chamber as read, leaving out its antlines, which are only drawn, so a chamber with none keeps the hash it had). Record one by completing the chamber in `npm run dev` and pressing Download solution in the completion dialog (development builds only; it refuses when the run doesn't replay the same way), which names the file by the chamber's permanent id (it matches the file's number), then move it next to the chamber. Record it again whenever its chamber file changes (the replay check reports a changed chamber; a change to its antlines alone needs none) or a rule change alters its route. Behaviour fixtures live in `scripts/fixtures/`, outside the catalogue: `fixtures.ts` pins, on tiny chambers of its own, how the rules play each change from the original rules and each element the original game didn't have (the light barrier, the blocked wall a link switches, the slide floor, the arrow a link turns, the emitter, its ray, the receiver and the mirror box), and each rule of the interaction table in `docs/elements.md` that no other fixture plays, so every rule there names its fixtures. Solver fixtures live in `scripts/solver_fixtures/`: tiny chambers that pass the layout checks, each with a fewest-moves and a fewest-portals route counted by hand (never by a search, since they are the reference the solver is checked against) and a short argument for why each count is optimal.
- **No test suite**: This project has no tests by design. TypeScript, the type-aware lint rules and the engine checks (the recorded solutions, behaviour fixtures and solver fixtures replayed by `npm run replay:check`, the solver check, and the random walk) are the safety net — do not weaken `strict` or `noUncheckedIndexedAccess`, and do not add `any` to silence an error.
- **TypeScript projects**: `tsconfig.json` only references `tsconfig.app.json` (browser, `src/`, extends `@vue/tsconfig/tsconfig.dom.json`), `tsconfig.node.json` (`vite.config.ts`, extends `@tsconfig/node24`) and `tsconfig.scripts.json` (Node without the DOM, extends `@tsconfig/node24`: `scripts/`, the rules in `src/game/rules/`, the solver in `src/solver/`, the shared files they import, the chamber JSON, the playground's and the fixture and solver fixture chambers; a file the scripts reach must be in its `include`, or the build fails; scripts import each other through its own `@scripts/` alias). An option the bases don't already cover must be set in all three.
- **Deploy**: `npm run deploy` runs `npm run verify` (which builds into `dist/`, git-ignored), stopping if any check fails, then `firebase deploy --only hosting` (project `portal-2d`); `npm run deploy -- -f` skips the checks and runs only `npm run build` before deploying. `firebase.json` rewrites every path to `/index.html` for history-mode routing.
- **Doc maintenance**: After changes, check whether `AGENTS.md`, `docs/elements.md`, `docs/game_summary.md`, `docs/level_design.md`, `docs/solver.md`, `docs/solving_by_hand.md` and `docs/sprites.md` need updating. `docs/level_design.md` grows with what we learn: whenever designing, changing or playing a chamber, or changing a rule or an element, turns up a new pitfall or tip for chamber design, add it there as a guideline, and fix or remove any guideline that no longer holds.

## TypeScript

- No semicolons. Single quotes. One class per file. Named exports.
- Files `snake_case`; classes, interfaces and type aliases `PascalCase`; functions and variables `camelCase`.
- Full descriptive names — no `el`, `p`, `btn`. Allowed short names: `i`, `j` (loop counters), `x`, `y` (coordinates), `dx`, `dy` (deltas), `ctx` (canvas context).
- Always import with the `@` alias (mapped to `src/`; scripts reach other scripts with `@scripts/`). No relative paths, no file extensions. `import type` for type-only imports.
- No object shorthand: write `{level: level}`, not `{level}` (enforced). Objects and arrays with two or more items go one per line (enforced).
- No TypeScript `enum`: use string-literal unions, with a const object when named values help.
- Indexing a `Record` or array yields `T | undefined`: handle the miss rather than asserting it away with `!`.
- Prefer getters over methods for parameterless functions that only read state.
- Unused parameters: `_`, `__`, `___`.
- Comments: a JSDoc block on every class and function (no types — TypeScript declares them), an end-of-line comment on each field's first declaration, plain comments above non-obvious logic.
